让 Coding Agent “给登录接口加一个限流功能”，一个代码能力很强、但没有流程约束的 Agent，多半会立刻搜到登录接口，写一个限流中间件，然后告诉你“功能已经完成”。代码也许能跑，可是按 IP 还是按账号限、多实例部署时计数器放在哪、Redis 挂了怎么办，这些问题它一个都没问。

开源项目 obra/superpowers 针对的就是这类情况。它把需求澄清、方案设计、实施计划、测试驱动开发、系统化调试、代码评审和完成验证，写成一组 Coding Agent 可以按场景触发、重复执行的 Skills。模型还是那个模型，文件和命令权限也没有增加，变的是 Agent 干活的流程。

<!--more-->

## 一个“加限流”需求背后的问题

“登录限流”几个字背后，至少藏着这些没回答的问题：

- 按 IP、账号、设备，还是多个维度共同限流？
- 一分钟内尝试 5 次就限制，还是连续失败 5 次才触发？
- 固定窗口、滑动窗口，还是令牌桶？
- 单实例还是多实例部署，计数器能不能只放在内存里？
- 服务在反向代理后面时，哪个 IP 才是真实客户端 IP？
- Redis 不可用时，放行、拒绝，还是降级到本地计数？
- 超限后返回什么状态码，要不要 Retry-After？
- 测试要覆盖哪些情况，怎么证明不同账号之间不会互相影响？

这些问题不先澄清，Agent 写出的代码即使能编译、能运行，也可能只是正确实现了一个错误的假设。现在的模型大多已经会写代码，难的是让它稳定地按可靠的工程流程交付。

## Superpowers 是什么

Superpowers 的正式名称是复数形式，官方把它定义为一套面向 Coding Agent 的完整软件开发方法论，由可组合的 Skills 和确保 Agent 使用这些 Skills 的初始指令共同组成，运行在 Codex、Claude Code、Cursor 等 Coding Agent 之上。

一个 Skill 是针对特定场景的操作规程，写明了触发条件、执行步骤、检查点和停止条件，比一句“请认真写测试”具体得多。这些 Skills 串起来是一条完整的开发链路：

```text
理解需求
   ↓
形成并确认设计
   ↓
编写可执行的实施计划
   ↓
建立隔离的开发环境
   ↓
按小任务实现和测试
   ↓
规格评审与代码质量评审
   ↓
运行最终验证
   ↓
合并、创建 PR、保留或清理分支
```

Agent 在不同阶段切换到对应的流程，检查条件没满足之前，不能随意跳到下一步。

### 它在系统里的位置

把 AI 编程系统粗略分层：最底下是基础模型（Codex、Claude、Gemini），负责理解、推理和生成；往上是 Agent 宿主或 Harness（Codex App、Claude Code、Cursor），管理上下文、工具、权限、循环和运行环境；再往外是工具与数据连接（内置工具、CLI、MCP Server）。Superpowers 处在“开发方法与流程”这一层，规定何时澄清、如何计划、怎样测试和验证。最外层是项目约束与反馈，也就是 AGENTS.md、测试、Lint、类型检查和 CI 提供的仓库事实和客观质量门槛。

所以它不训练模型、不改权重，也不是 IDE 或宿主，文件读写、终端执行、子 Agent、Git 和权限控制都由宿主提供。它也不是 MCP：MCP 解决 Agent 能连接哪些工具和数据源，Superpowers 解决按什么方法完成任务，装上它不会多出数据库权限，也不替代工具本身的鉴权和安全边界。两者可以一起用，比如通过 MCP 查询工单，再用 brainstorming 澄清需求。

最容易混淆的是它和 AGENTS.md。AGENTS.md 描述这个项目的事实和规则：用什么框架、目录怎么组织、该跑哪些命令、哪些文件不能动。Superpowers 描述跨项目复用的工作方法：遇到功能需求先做什么、设计怎么变成计划、失败后怎么调查、完成前怎么验证。两者谁也替代不了谁，缺了项目文档，Agent 照样可能按一套规范流程做出不符合仓库约定的修改。

## 为什么更强的模型仍然需要流程

Coding Agent 出问题，很多时候不是不会写代码，而是一些稳定的行为倾向在起作用。收到需求就动手，把需求里的空白自动补成看似合理的假设；代码一旦写出来，后续讨论就容易围着已有实现打转，方向错了也倾向于继续修补。需求同时涉及接口、数据库、前端、测试和部署时，它会在同一个上下文里不停搜索、修改、解释，任务越长，早期约束越容易被挤出注意力。看到报错就改最可疑的一行，不行再加条件、加重试、加兜底，表面症状没了，根因却被掩盖了。

刚写完的代码让它自己评价，它检查的往往是“我写的东西是否自洽”，很少回头确认“我写的是不是用户要的”。模型还能根据代码的样子推测它大概能跑，但没真正执行测试、构建和静态检查，“已修复”“全部通过”“可以合并”都只是声明。Superpowers 针对这几类问题分别设计了流程。

## Skill 里写了什么

每个 Skill 先写明触发条件。当前版本的 test-driven-development 用于实现任何新功能、Bug 修复、重构和行为变更，要求在写实现代码之前触发；systematic-debugging 用于遇到 Bug、测试失败或异常行为时；verification-before-completion 用于准备声称任务完成、问题修复或测试通过之前。

然后是明确的操作顺序。以 TDD 为例，Skill 不只说“采用 TDD”，还规定：

```text
RED：先写一个最小失败测试
  ↓
确认测试确实以预期原因失败
  ↓
GREEN：只写让测试通过所需的最少代码
  ↓
确认当前测试和完整测试集通过
  ↓
REFACTOR：在保持绿色的前提下整理代码
```

顺序本身就是规则：测试先失败，才能证明它真的能捕捉尚未实现的行为；实现写完再补测试，很容易只验证了刚写出来的实现。

不少 Skills 还带硬性检查点：设计没经过用户确认，不能进入实现；没完成根因调查，不能开始修复；任务评审没有同时通过规格和质量检查，不能标记完成；没运行新鲜的验证命令，不能声称测试通过；测试失败时，不能继续合并或标记完成。这里的“硬性”只是方法内部的要求，插件并没有高于用户的控制权。官方规则明确写了，用户的直接指令和项目指令优先于 Skills，是否批准例外由人决定。

我觉得比较有意思的是反合理化规则。Agent 常给自己找的理由，比如“这只是个很小的改动”“先快速修一下，之后再调查”“代码看起来没问题”“刚才已经跑过测试”，Skills 会直接列出来，并解释为什么它们不能成为跳过流程的理由，提前把绕过流程的借口堵上。

最后，流程要落到可观察的证据上：设计文档和实施计划、失败与通过的测试输出、每个任务的代码差异、评审结论、构建/Lint/类型检查/测试命令的退出状态、分支和 PR 状态。质量判断不再只依赖 Agent 的自述。

## 一条完整的工作流

下面按当前 v6.1.1 的 Skill 契约，把完整工作流顺一遍。

### 入口：先找对应的 Skill

using-superpowers 是整个系统的入口，要求 Agent 在回复、提问或执行动作之前，先判断当前任务有没有相关 Skill。Skills 光存在不够，Agent 如果还是按老习惯直接动手，技能库就只是一堆没人执行的文档。不同宿主会通过原生 Skill 发现、插件机制或会话初始化来暴露这些能力，用户正常描述任务即可，不需要每次手动报出 Skill 名称。

### 需求与设计：brainstorming

用户说“做一个功能”时，brainstorming 不允许 Agent 立刻写代码。它会先检查项目现状和已有约定，逐个澄清目的、约束和成功标准，提出两到三种方案比较取舍，分段展示设计并等待确认；确认后写成设计文档，检查有没有占位符、矛盾、范围过大或歧义，再请用户审阅书面规格，批准后才进入实施计划。模型并不缺方案，它的毛病是问题定义还没确认就先选了一个。

### 实施计划：writing-plans

writing-plans 把批准的设计拆成小任务：写出准确的文件路径和每个文件的职责，列出任务之间消费和产出的接口，把每一步缩小到大约 2 到 5 分钟的动作，给出实际的测试代码、执行命令和期望结果，不允许出现“稍后实现”“补充适当错误处理”这类占位描述。每个任务都是一个可以独立测试和评审的交付单元。计划写得细，实施阶段大量临场的架构判断就提前解决了，后面的 Agent 照着清楚的规格施工，不用边写边猜。

### 隔离工作区：using-git-worktrees

开始执行前，using-git-worktrees 会先判断当前环境是否已经隔离。宿主有原生工作区能力就优先用宿主的，否则回退到 Git Worktree。如果用户或项目指令没有预先声明 Worktree 偏好，当前 Skill 要求创建前先征得用户同意；用户拒绝，就在现有工作区继续完成环境设置和基线验证。环境建好后要完成项目安装并跑一遍基线测试，这样才能分清失败是修改前就有的，还是这次修改引入的。隔离也让多个任务或 Agent 能在清晰的边界里工作。

### 执行：子 Agent 与 TDD

执行有两种方式。subagent-driven-development 为每个任务派发一个新的实现 Agent，完成后做任务级评审；executing-plans 用在不采用逐任务子 Agent 的时候，按计划逐项或分批执行，并保留检查点。宿主支持子 Agent 时，官方更倾向前者：主 Agent 保存全局计划、组织任务、处理交接，每个实现 Agent 只拿当前任务需要的上下文，不必背着所有搜索过程、失败尝试和历史讨论干活。

“每个任务一个新 Agent”不等于让它们同时改同一个工作区。默认是一个任务做完、评审通过，再进入下一个；只有工作彼此独立、不会产生文件或状态冲突时，才适合并行派发。

每个行为都按 TDD 实现。当前 test-driven-development 的规则很严：新功能、Bug 修复、重构和行为变更默认都要先写测试，亲眼看到它因为缺少目标行为而失败，再写最少的实现让它通过。官方列出的例外包括一次性原型、生成代码和配置文件，但需要先询问人类协作者，不能由 Agent 自己认定“这次可以跳过”。

### 调试：systematic-debugging

测试失败或行为异常时，systematic-debugging 要求依次走四个阶段：

- 根因调查：阅读错误、稳定复现、检查最近变化并收集跨组件证据；
- 模式分析：找一个正常的实现作参照，比较差异；
- 假设与实验：一次只提一个根因假设，用最小变化验证；
- 实施修复：为根因写失败测试，再修复并完整验证。

连续几次修复都失败，流程要求回头审视架构或问题定义，不能继续叠补丁。

### 评审：规格和质量分开看

在 Subagent-Driven Development 中，每个任务完成后都要经过任务级评审。当前 v6 流程由一个任务 Reviewer 同时给出两个结论，并不分别启动两个 Reviewer：一是规格符合性，是否完整实现了要求、有没有遗漏或超出范围；二是代码质量，实现是否清晰、可维护、经过适当测试，有没有重要风险。发现关键问题就派发修复并重新评审，所有任务结束后，再对整个分支做一次最终评审。

这两件事有必要分开看。一段代码可以很优雅却解决了错误的问题，也可以满足表面需求却留下严重的维护和安全风险。

### 完成：用本次的验证结果说话

verification-before-completion 的核心规则是：没有本次刚执行得到的验证结果，就不能做出完成声明。Agent 说“测试全部通过”之前，必须找出哪条命令能证明这句话，执行完整命令，读完全部输出并确认退出状态。以前跑过、只跑了一个子集、另一个 Agent 说通过了、代码看起来没问题，都不能替代当前验证。

之后 finishing-a-development-branch 会再验证一次测试，让用户选择怎么处理当前工作：本地合并、推送并创建 PR、保留分支，或者在明确确认后丢弃。

按当前官方 README，内置 Skills 大致如下：

| 类别 | Skill | 主要职责 |

| 入口 | using-superpowers | 在行动前发现并调用相关 Skill |

| 计划 | writing-plans | 把设计拆成精确、可测试、可评审的实施任务 |

| 并行协作 | dispatching-parallel-agents | 将彼此独立的问题并行交给多个 Agent |
| 测试 | test-driven-development | 执行 RED-GREEN-REFACTOR |
| 调试 | systematic-debugging | 先定位根因，再进行最小验证和修复 |
| 评审 | requesting-code-review | 发起结构化代码评审 |

## 用登录限流走一遍

回到开头的需求，用一个简化示例看看 Superpowers 会怎样改变执行过程。

Agent 不会马上改代码。它先读项目结构和现有认证逻辑，然后一次讨论一个关键问题：限流是为了防单账号暴力破解，还是防单个 IP 扫描大量账号？服务是否多实例部署，有没有现成的 Redis？只统计失败请求，还是所有登录请求？触发后多久恢复？Redis 故障时安全优先还是可用性优先？假设最终确认的需求是：

- 按“账号 + 客户端 IP”组合限流；
- 5 分钟内连续失败 5 次后，阻止后续登录尝试 15 分钟；
- 多实例共享 Redis；
- 成功登录后清除失败计数；
- 触发限制时返回 429 和 Retry-After；
- Redis 故障时记录告警并拒绝登录，避免保护失效。

到这里，讨论的对象已经从模糊的“加限流”变成了一组可以设计和验证的行为。接下来 Agent 会比较几种方案，不会默认选第一个想到的实现：

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 进程内 Map | 实现简单，无外部依赖 | 多实例不共享，重启后状态丢失 |
| Redis 固定窗口 | 结构简单，容易使用原子计数 | 窗口边界可能出现突发请求 |
| Redis 滑动窗口或有序集合 | 行为更精确，可记录失败时间 | 操作和清理逻辑更复杂 |

结合多实例部署和安全要求，最终选择 Redis 有序集合记录 5 分钟内的失败时间，并用单独的封禁 Key 保存 15 分钟封禁状态。计数、清理过期记录和触发封禁通过 Lua 脚本保持原子性；账号先做规范化和不可逆摘要，再参与 Key 计算，避免直接暴露身份信息。

计划不会只写一句“实现限流并添加测试”。下面假设这是一个 Node.js 项目，只展示计划摘要，真实的 writing-plans 产物还会写出完整代码片段、每一步的期望输出和提交动作：

```text
任务 1：新增 LoginAttemptLimiter 接口及 Redis 实现
  - 文件：src/auth/login-attempt-limiter.ts
  - 测试：tests/auth/login-attempt-limiter.test.ts
  - 写失败测试：记录第 5 次失败后，下一次检查返回 blocked 状态
  - 运行：npm test -- tests/auth/login-attempt-limiter.test.ts
  - 预期：FAIL，提示 LoginAttemptLimiter 尚未实现
  - 实现最小 Redis 操作
  - 重新运行同一测试，预期 PASS

任务 2：把限流器接入登录服务
  - 文件：src/auth/login-service.ts
  - 测试：tests/auth/login-service.test.ts
  - 写失败测试：被限制时不再校验密码
  - 写失败测试：成功登录清除失败计数
  - 实现最小接入代码
  - 运行：npm test -- tests/auth

任务 3：增加 HTTP 429 响应和 Retry-After
  - 文件：src/http/login-controller.ts
  - 测试：tests/http/login-controller.test.ts
  - 写接口测试
  - 实现响应映射
  - 运行接口测试、Lint 和构建
```

执行时，Agent 先加一个行为测试：

```javascript
it('blocks login after five failed attempts within five minutes', async () => {
  clock.set('2026-07-13T10:00:00Z');
  await failLogin({ account: 'alice', ip: '203.0.113.8' }, 5);

  const result = await login({
    account: 'alice',
    password: 'wrong-password',
    ip: '203.0.113.8'
  });

  expect(result.status).toBe('rate_limited');
  expect(result.retryAfterSeconds).toBe(900);
});
```

然后实际运行，确认它因为限流行为尚未实现而失败，这个测试才有资格进入 GREEN 阶段。这段代码只演示“累计 5 次失败后阻止后续请求”这一个行为，完整测试还应覆盖 5 分钟统计窗口、15 分钟到期恢复、成功登录清零、不同账号与 IP 组合相互隔离、Redis 故障策略，以及并发请求下的原子性。

如果宿主支持子 Agent，主 Agent 会把“Redis 限流器”“认证服务接入”“HTTP 响应”按计划逐个交给不同的任务 Agent，每个只拿当前任务、接口约束和必要的项目上下文。任务完成后，评审 Agent 会检查：是否确实在累计 5 次失败后才限制后续尝试，成功登录是否清除了状态，不同账号和 IP 是否隔离，有没有错误地记录明文账号或密码，Redis 操作是否存在竞态，有没有实现计划之外的复杂策略。发现问题先修复再重新评审，不能用“总体上差不多”放行。

宣布完成之前，Agent 要运行项目实际使用的验证命令，例如：

```bash
npm test
npm run lint
npm run typecheck
npm run build
```

并根据真实输出报告哪些命令通过、执行了多少测试、是否仍有警告或已知问题。

## 为什么这套方法可能有效

资深工程师都知道“先确认边界”“先复现再修”“合并前再跑一次完整测试”，但这些习惯常被当成不言自明的常识。对 Agent 来说，常识没进入当前上下文，就不一定会执行，Skills 把它们写成了触发条件、步骤和检查表。阶段门槛则把问题拦在当前阶段：需求误解在写代码前发现，修正成本可能只是几轮对话；等接口、数据库和测试都写完再发现，返工就贵得多。实现和评审分给不同 Agent，即使用的是同一个模型，新的上下文和不同角色也能减少“沿着原有思路自我证明”的偏差。设计、计划、测试结果和评审结论连成一条可追踪的链路，任务失败时更容易判断问题出在哪个阶段。

## 它解决不了的问题

用户确认的需求本身就错了，Agent 会非常规范地实现错误需求。brainstorming 能帮忙暴露假设，但替不了业务负责人决定产品方向。测试全绿也只说明代码满足了这些测试表达的条件，测试漏掉竞态、安全边界、真实依赖或部署差异，绿色结果就是假安全感。

Skills 终究要靠模型理解和遵守。强硬措辞、检查表和宿主集成能提高一致性，但达不到编译器级别的强制。真正不能越过的权限、数据范围和发布门槛，还是应该由沙箱、鉴权、代码所有者规则和 CI 来实现。

成本也是实打实的。澄清需求、写文档、派发子 Agent、多轮评审、重复验证都会增加时间、Token 和调用次数。复杂功能上这些成本可能换来更少返工，改一行文案或者明确的机械修改走完整流程就显得很重。Superpowers 的取舍很明确：优先降低漏项和错误完成的概率，不追求第一眼看到代码的速度。

严格 TDD 也不适合所有产物。官方默认要求功能、Bug 修复、重构和行为变更执行 TDD，把一次性原型、生成代码和配置文件列为需要人类批准的例外。缺少测试基础的遗留系统、纯视觉探索或研究性实验，团队可能要自己划定边界；但如果自行弱化了规则，就应该明确这是团队对方法论的调整，别再声称仍在完整执行默认流程。

子 Agent 和 Worktree 依赖宿主条件。没有子 Agent 时仍可以用 executing-plans 顺序执行，需求澄清、计划、TDD、系统化调试和完成验证照样有价值，只是上下文隔离和独立评审的效果会变弱。没有 Git 仓库、测试命令或可复现环境，部分工作流也发挥不出完整价值。

第三方 Skill 要像代码一样审查。Skill 会影响 Agent 的决策，有些插件还附带脚本和运行时集成，安装、升级或引入自定义 Skill 前，应检查来源、内容、执行权限和网络行为，不要因为它看起来只是 Markdown 就默认没有供应链风险。官方 README 还说明，brainstorming 的可选 Visual Companion 默认会从项目网站加载带版本号的品牌图片，用于粗略统计版本使用情况；它不包含项目、Prompt 或点击信息，可以通过 SUPERPOWERS_DISABLE_TELEMETRY 等环境变量关闭。对网络访问敏感的团队，引入前最好确认这类默认行为。

## 适合什么任务

涉及多个文件或模块的新功能、线上 Bug 和间歇性失败的测试、有明确行为约束又容易回归的重构、认证/支付/权限/数据迁移这类高风险模块、需要多个 Agent 分工并保留评审链路的长任务，都比较适合用 Superpowers；想把团队工程习惯沉淀成可复用流程的项目也一样。

一次性探索原型、纯配置或生成文件修改、明确的文案注释和格式调整、没有可运行测试或可复现环境的仓库、还在发散研究阶段的实验，流程成本会比较明显。不过任务简单不代表可以虚构完成结果，即使对小任务用更轻的流程，最终验证也应该和风险相匹配。

## 安装

以下信息基于 2026 年 7 月 13 日的官方 README：Superpowers 上游仓库当时的最新正式版本为 v6.1.1，项目由 Jesse Vincent 和 Prime Radiant 团队维护，采用 MIT License。插件市场中的打包版本可能晚于上游 Release，安装方式和实际版本都应以对应宿主的市场页面为准。

Codex App：在侧边栏打开 Plugins，搜索 Superpowers，点击旁边的 + 并按提示安装。当前 v6.1.1 插件清单将它归在 Developer Tools 分类。

Codex CLI：打开插件搜索界面，搜索 superpowers，然后选择 Install Plugin。

```text
/plugins
```

Claude Code：Superpowers 已进入 Claude 官方插件市场，可以执行：

```text
/plugin install superpowers@claude-plugins-official
```

Cursor：在 Agent 对话中执行下面的命令，或者直接在插件市场搜索 superpowers。

```text
/add-plugin superpowers
```

官方 README 还列出了 Antigravity、Factory Droid、GitHub Copilot CLI、Kimi Code、OpenCode 和 Pi 等宿主。同时用多个宿主时需要分别安装，在一个工具里装好，其他工具并不会自动共享。

装好后照常提任务就行，比如“为当前项目增加密码重置功能”。如果技能被正确发现，Agent 通常不会马上改代码，而是先检查项目上下文、澄清设计。也可以直接点名某个 Skill，比如要求用 systematic-debugging 调查一个间歇性失败。

## 在团队里试点

团队引入的话，我更倾向于先挑一个中等复杂度的任务做有指标的试点：有真实的设计取舍、涉及多个文件、有可运行的测试，但不要一上来就选最关键的生产迁移。

开始前有几件事要做。先审查 Skills 和插件内容，确认它会读写什么、执行哪些脚本、是否访问网络，和团队安全政策是否兼容。再把构建命令、测试分层、目录边界、提交规范和安全要求写进 AGENTS.md 或等效文档，通用工作流不知道你的业务事实。还要明确例外由谁批准，比如哪些任务可以不走 TDD、什么情况下不用 Worktree、哪些命令需要人工确认、哪些目录禁止 Agent 修改。最后记录使用的版本，Skill 内容变化会改变 Agent 行为，升级时要像升级 Linter、构建插件或 CI Action 一样阅读 Release Notes、评估重要变更。

评估效果要看结果：需求澄清后的返工次数、Code Review 中发现的重要问题、逃逸到主分支或生产环境的缺陷、完整任务周期（不只是首次生成代码的时间）、测试和验证覆盖、Token 与模型调用及人工等待成本、长任务中断后能否恢复。如果缺陷和返工没有下降，只是文档和调用次数多了，就该回头看这些 Skills 是否适合当前项目，流程变长本身不算成功。

Superpowers 做的事情其实很朴素：把资深工程师默认会做的那些步骤写下来，再要求 Agent 每一步都拿出证据。它能减少流程失控和虚假完成，但需求是否正确、测试是否靠谱，以及权限边界、CI 和人工判断，仍然要团队自己把好关。
