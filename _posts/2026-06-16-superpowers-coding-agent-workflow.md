Superpowers 并没有让大模型获得新的智力，也没有给它增加新的文件或命令权限。它做的，是把需求澄清、方案设计、实施计划、测试驱动开发、系统化调试、代码评审和完成验证，组织成一套 Coding Agent 可以重复执行的工程流程。

<!--more-->

本文讨论的是开源项目 obra/superpowers，不是泛指英语里的“超能力”。它的正式名称是复数 Superpowers，官方将它定义为一套面向 Coding Agent 的完整软件开发方法论，由可组合的 Skills 和确保 Agent 使用这些 Skills 的初始指令共同组成。

## 先从一个常见任务说起

假设你对 Coding Agent 说：

> 给登录接口加一个限流功能。

一个代码能力很强、但缺少工程流程约束的 Agent，可能立刻搜索登录接口，创建一个限流中间件，然后告诉你“功能已经完成”。

问题在于，“登录限流”背后藏着很多尚未回答的问题：

- 按 IP、账号、设备，还是多个维度共同限流？
- 允许一分钟尝试 5 次，还是连续失败 5 次才触发？
- 使用固定窗口、滑动窗口，还是令牌桶？
- 项目是单实例还是多实例部署，计数器能不能只放在内存里？
- 服务运行在反向代理后面时，哪个 IP 才是真实客户端 IP？
- Redis 不可用时，是放行、拒绝，还是降级到本地计数？
- 超过限制后返回什么状态码，是否需要 Retry-After？
- 应该覆盖哪些测试，如何证明不同账号之间不会互相影响？

如果这些问题没有先被澄清，Agent 即使写出能够编译、能够运行的代码，也可能只是正确实现了一个错误的假设。

这正是 Superpowers 想解决的核心矛盾：

模型可能已经会写代码，但它不一定会稳定地按照可靠的软件工程流程交付代码。

代码生成只是软件开发的一部分。真正决定结果是否可信的，往往是需求有没有说清楚、方案是否经过比较、任务是否合理拆分、测试是否先验证失败、调试是否找到根因、代码是否经过独立评审，以及“已经完成”是否有新鲜的验证证据。

## 一句话解释 Superpowers

可以先给出一个工程化定义：

Superpowers 是运行在 Codex、Claude Code、Cursor 等 Coding Agent 之上的技能框架和软件开发方法论。它用一组带有触发条件、执行步骤、检查点和停止条件的 Skills，约束 Agent 如何完成软件开发任务。

这里有两个关键词。

第一个关键词是 Skill。一个 Skill 不是简单的一句“请认真写测试”，而是一份针对特定场景的操作规程。例如：

- 遇到新功能时，先使用 brainstorming 澄清需求和设计；
- 有了设计后，使用 writing-plans 把工作拆成可验证的小任务；
- 实现功能或修复 Bug 时，使用 test-driven-development 执行 RED-GREEN-REFACTOR；
- 遇到异常时，使用 systematic-debugging 先找根因，再修改代码；
- 准备宣布完成时，使用 verification-before-completion 运行能够证明结论的命令。

第二个关键词是 方法论。这些 Skills 并不是彼此独立的提示词片段，而是可以串成一条完整的开发链路：

```text
理解需求
   ↓
形成并确认设计
   ↓
编写可执行的实施计划
   ↓
建立隔离的开发环境
   ↓
按小任务实现和测试
   ↓
规格评审与代码质量评审
   ↓
运行最终验证
   ↓
合并、创建 PR、保留或清理分支
```

因此，Superpowers 的重点不是“再给模型一段更长的 Prompt”，而是让 Agent 在不同阶段切换到对应的工程流程，并且在满足检查条件之前不能随意跳到下一步。

## Superpowers 不是什么

理解一个新概念时，先排除几个常见误解会更清楚。

### 1. 它不是一个新的大语言模型

Superpowers 不负责训练模型，也不会改变模型权重。安装前后，真正完成推理和代码生成的仍然是 Codex、Claude、Gemini 或其他宿主支持的模型。

它改变的是模型的工作方式，不是模型的基础智力。

### 2. 它不是 IDE，也不是 Coding Agent 宿主

Superpowers 需要运行在 Codex App、Codex CLI、Claude Code、Cursor、Kimi Code 等宿主中。文件读写、终端执行、子 Agent、Git 和权限控制，仍由宿主环境提供。

### 3. 它不是 MCP，也不会凭空增加工具

MCP 主要解决“模型能够连接哪些工具和数据源”的问题，例如让 Agent 查询数据库、访问工单系统或调用浏览器。

Superpowers 主要解决“Agent 应该按什么方法完成任务”的问题。它不会因为安装后就自动获得数据库权限，也不会替代工具本身的鉴权和安全边界。

### 4. 它不是一个万能 Prompt

普通 Prompt 通常只作用于当前请求。Superpowers 则把流程拆成多个按场景加载的 Skills，并通过前置条件、硬性规则、评审循环和验证要求把它们组合起来。

从实现形式看，Skill 仍然包含自然语言指令；但从工程作用看，它更像一套可以被 Agent 执行的标准作业程序，而不是一句临时建议。

### 5. 它不能保证代码永远正确

错误的需求、缺失的运行环境、失真的测试、过期的项目文档和不充分的权限设计，仍然会导致错误结果。Superpowers 能减少随意行动和未经验证的结论，但它不是形式化验证系统，也不是生产安全的替代品。

## 它位于 AI 编程系统的哪一层

可以把一套 AI 编程系统粗略拆成下面几层：

| 层次 | 主要职责 | 典型例子 |
| --- | --- | --- |
| 基础模型 | 理解、推理、生成代码和文本 | Codex、Claude、Gemini |
| Agent 宿主 / Harness | 管理上下文、工具、权限、循环和运行环境 | Codex App、Claude Code、Cursor |
| 工具与数据连接 | 提供文件、终端、浏览器、数据库和业务系统能力 | 内置工具、CLI、MCP Server |
| 开发方法与流程 | 规定何时澄清、如何计划、怎样测试和验证 | Superpowers |
| 项目约束与反馈 | 提供仓库事实和客观质量门槛 | AGENTS.md、测试、Lint、类型检查、CI |

Superpowers 位于“开发方法与流程”这一层。它连接了模型能力和项目反馈：一方面告诉 Agent 下一步应该怎么做，另一方面要求 Agent 用测试结果、命令输出和代码差异来证明自己做对了。

可以把它理解成：

模型决定 Agent 理论上能做多难的事，Superpowers 试图决定它是否会用一套稳定的方法把事情做完。

## 为什么更强的模型仍然需要工程流程

很多 Coding Agent 的失败，并不是因为模型完全不会写代码，而是因为它在执行过程中存在一些稳定的行为倾向。

### 1. 行动偏好：还没想清楚就开始修改

Agent 收到“增加功能”后，很容易把“快速产生代码”当成主要目标。需求中的空白会被自动补成看似合理的假设，而这些假设往往没有经过用户确认。

代码出现得越早，后续讨论越容易围绕已有实现展开。即使最初方向不对，人和 Agent 也可能因为已经投入了修改成本而继续修补。

### 2. 大任务容易变成一次性生成

当一个需求同时涉及接口、数据库、前端、测试和部署配置时，Agent 可能在同一个上下文中不断搜索、修改和解释。任务越长，早期约束越容易被挤出注意力中心，遗漏和相互矛盾的实现也越多。

### 3. 调试容易退化为猜测性补丁

看到报错后直接修改最可疑的一行，再运行一次；不行就继续加条件、重试或兜底。这种方式偶尔能够消除表面症状，却可能掩盖真正的根因，并引入新的异常路径。

### 4. 生成者不擅长独立评价自己的结果

同一个 Agent 刚刚写完代码，又立刻判断“实现完全符合需求”，容易受到自己原有思路的影响。它可能检查“我写的代码是否自洽”，却没有重新检查“我是否写了用户真正需要的东西”。

### 5. “应该可以”很容易被说成“已经完成”

模型能够根据代码形状推测它大概率能运行，但推测不是证据。没有真正执行测试、构建和静态检查时，“已修复”“全部通过”“可以合并”都只是未经验证的声明。

Superpowers 的思路，是把这些行为问题分别交给不同的流程处理，而不是只在系统 Prompt 里写一句“请谨慎”。

## Superpowers 具体解决了哪些问题

| 常见问题 | 对应机制或 Skill | 带来的改善 | 仍然存在的边界 |
| --- | --- | --- | --- |
| 需求不清就开写 | brainstorming | 先确认目标、约束、方案和验收标准 | 关键产品决策仍要由人判断 |
| 一个大任务一次性实现 | writing-plans | 拆成边界明确、可以单独验证的小任务 | 计划本身也可能遗漏事实 |
| 修改污染当前工作区 | using-git-worktrees | 优先在隔离工作区和独立分支中开发 | 依赖 Git 和宿主环境支持 |
| 先写实现，最后补测试 | test-driven-development | 强制先看到测试以正确原因失败 | 低质量测试仍可能给出虚假信心 |
| 报错后连续尝试补丁 | systematic-debugging | 先复现、收集证据、形成单一假设，再修根因 | 无法复现时仍可能卡住 |
| 长任务上下文越来越混乱 | subagent-driven-development | 每个任务使用新的执行 Agent，并保留主 Agent 的协调上下文 | 增加调用次数和交接成本 |
| 实现偏离规格或过度开发 | 任务级评审 | 分别检查规格符合性和代码质量 | 评审 Agent 也可能判断错误 |
| 没跑命令就宣布完成 | verification-before-completion | 要求用本次重新执行的完整命令输出支持结论 | 验证命令覆盖不到的风险仍存在 |
| 做完后分支处理随意 | finishing-a-development-branch | 测试通过后再选择合并、PR、保留或丢弃 | 最终发布策略仍由团队决定 |

它没有消灭这些风险，而是把原本依赖个人习惯的动作变成显式步骤，让错误更早暴露，让过程更容易检查和复盘。

## 核心机制：Skill 不是一句建议，而是一份流程契约

Superpowers 的每个 Skill 通常包含几类信息。

### 1. 触发条件

Skill 会说明自己在什么情况下使用。例如，当前版本的 test-driven-development 明确用于实现任何新功能、Bug 修复、重构和行为变更，并要求在编写实现代码之前触发。

systematic-debugging 则用于遇到 Bug、测试失败或异常行为时。verification-before-completion 用于准备声称任务完成、问题修复或测试通过之前。

### 2. 明确的操作顺序

Skill 不只说“采用 TDD”，还规定：

```text
RED：先写一个最小失败测试
  ↓
确认测试确实以预期原因失败
  ↓
GREEN：只写让测试通过所需的最少代码
  ↓
确认当前测试和完整测试集通过
  ↓
REFACTOR：在保持绿色的前提下整理代码
```

顺序本身就是规则的一部分。测试先失败，才能证明它真的能够捕捉尚未实现的行为；如果实现代码已经存在，再补测试，很容易只验证自己刚刚写出的实现。

### 3. 硬性检查点

不少 Skills 带有明确的硬门槛。例如：

- 设计没有经过用户确认，就不能进入实现；
- 没完成根因调查，就不能开始修复；
- 任务评审没有同时通过规格和质量检查，就不能标记完成；
- 没有运行新鲜的验证命令，就不能声称测试通过；
- 测试失败时，不能继续合并或创建完成状态。

这些规则的价值在于，它们降低了 Agent 为了快速推进而跳过关键步骤的概率。

这里的“硬性”是指 Superpowers 方法内部的执行要求，不代表插件获得了高于用户的控制权。官方规则同时明确：用户的直接指令和项目指令优先于 Skills；是否批准例外，最终仍由人决定。

### 4. 反合理化规则

Agent 常见的自我解释包括：“这只是一个很小的改动”“先快速修一下，之后再调查”“代码看起来没问题”“刚才已经跑过测试”。

Superpowers 的 Skills 会直接列出这些常见说法，并解释为什么它们不能成为跳过流程的理由。这是一种针对模型行为特点设计的约束：不仅告诉它该做什么，也提前堵住它可能用来绕过流程的理由。

### 5. 可观察证据

流程最终需要落到可以观察的事实上，例如：

- 设计文档和实施计划；
- 失败测试与通过测试的输出；
- 每个任务的代码差异；
- 规格评审和代码质量评审结论；
- 构建、Lint、类型检查和测试命令的退出状态；
- 分支、提交和 Pull Request 状态。

这使质量判断不再只依赖 Agent 的自然语言自述。

## 一条完整的 Superpowers 工作流

结合当前 v6.1.1 的 Skill 契约，一条完整工作流可以整理成下面九个阶段。

### 第一阶段：先检查应该使用哪个 Skill

using-superpowers 是整个系统的入口。它要求 Agent 在回复、提问或执行动作之前，先判断当前任务是否存在相关 Skill。

这一步很关键。只有 Skills 存在还不够，如果 Agent 仍然按照原来的习惯直接行动，技能库就只是一组没有被执行的文档。

不同宿主会通过原生 Skill 发现、插件机制或会话初始化方式暴露这些能力。用户正常描述任务即可，理论上不需要每次手动背出 Skill 名称。

### 第二阶段：通过 Brainstorming 把想法变成设计

当用户提出“做一个功能”时，brainstorming 不允许 Agent 立刻写代码。它会先：

- 检查项目现状和已有约定；
- 逐个澄清目的、约束和成功标准；
- 提出两到三种方案并比较取舍；
- 分段展示设计，等待用户确认；
- 把确认后的结果写成设计文档；
- 检查文档中是否存在占位符、矛盾、范围过大或歧义。

请用户再次审阅书面规格，获得批准后再进入实施计划。
它解决的不是“模型想不到方案”，而是“模型在没有确认问题定义之前就选择了一个方案”。

### 第三阶段：把设计写成可执行计划

writing-plans 会把已经批准的设计拆成小任务。当前方法论强调：

- 写出准确的文件路径；
- 说明每个文件的职责；
- 列出任务之间消费和产出的接口；
- 把每个步骤缩小到大约 2 到 5 分钟的动作；
- 给出实际测试代码、执行命令和期望结果；
- 不使用“稍后实现”“补充适当错误处理”之类的占位描述；
- 每个任务都形成一个可独立测试和评审的交付单元。

高质量计划的作用，是把实施阶段的大量临场架构判断提前解决，让后续 Agent 更接近“按清楚的规格施工”，而不是边写边猜。

### 第四阶段：在执行前建立隔离工作区

真正开始执行计划时，using-git-worktrees 会先判断当前环境是否已经隔离。如果宿主提供原生工作区能力，则优先使用宿主能力；否则可以回退到 Git Worktree。若用户或项目指令没有预先声明 Worktree 偏好，当前 Skill 要求在创建前先征得用户同意；用户拒绝时则在现有工作区继续完成环境设置和基线验证。

创建环境后，它还要求完成项目安装，并运行基线测试。这样可以区分：

- 修改前项目本来就失败；
- 还是修改之后才引入失败。

隔离的价值不仅是避免弄乱当前分支，也让多个任务或 Agent 能够在清晰的边界中工作。

### 第五阶段：按计划执行

Superpowers 提供两种主要方式：

- subagent-driven-development：为每个任务派发一个新的实现 Agent，再进行任务级评审；
- executing-plans：不采用逐任务子 Agent 时，按计划逐项或分批执行，并保留检查点。

如果宿主支持子 Agent，官方流程更倾向于使用 Subagent-Driven Development。主 Agent 负责保存全局计划、组织任务和处理交接；每个实现 Agent 只接收当前任务需要的上下文。

“每个任务使用一个新 Agent”不等于让所有实现 Agent 同时修改同一个工作区。默认流程是完成一个任务、通过任务评审，再进入下一个任务；只有工作彼此独立、不会产生文件或状态冲突时，才适合使用并行派发。

这种方式试图解决长会话中的上下文污染：一个 Agent 不必同时记住所有搜索过程、失败尝试和历史讨论，而可以在相对干净的上下文里完成一个小任务。

### 第六阶段：用 TDD 实现每个行为

当前 test-driven-development Skill 的规则非常严格：新功能、Bug 修复、重构和行为变更默认都执行 TDD。

它的核心不是“项目里最后有测试”，而是：

先写测试，亲眼看到它因为缺少目标行为而失败，再编写最少实现使其通过。

官方列出的例外包括一次性原型、生成代码和配置文件，但需要先询问人类协作者，而不是由 Agent 自行认定“这次可以跳过”。

### 第七阶段：失败时进行系统化调试

如果测试失败或行为异常，流程不会直接进入“继续改代码”。systematic-debugging 要求依次完成四个阶段：

- 根因调查：阅读错误、稳定复现、检查最近变化并收集跨组件证据；
- 模式分析：寻找正常实现作为参照，比较差异；
- 假设与实验：一次只提出一个根因假设，用最小变化验证；
- 实施修复：为根因创建失败测试，再修复并完整验证。

如果连续多个修复尝试都失败，流程要求重新审视架构或问题定义，而不是继续叠加补丁。

### 第八阶段：进行任务评审和最终评审

在 Subagent-Driven Development 中，每个任务完成后都要经过任务级评审。当前 v6 流程由一个任务 Reviewer 同时返回两个结论，而不是分别启动两个 Reviewer：

- 规格符合性：是否完整实现了要求，有没有遗漏或超出范围；
- 代码质量：实现是否清晰、可维护、经过适当测试，是否存在重要风险。

发现关键问题后，流程会派发修复并重新评审。所有任务结束后，还会进行一次覆盖整个分支的最终评审。

把“是否做对需求”和“代码写得是否合理”分开很重要。一段代码可以很优雅，却解决了错误的问题；也可以满足表面需求，却留下严重的维护和安全风险。

### 第九阶段：用本次验证结果完成交付

verification-before-completion 的核心规则是：

没有本次刚执行得到的验证结果，就不能做出完成声明。

Agent 在说“测试全部通过”之前，必须识别哪条命令能够证明这句话，执行完整命令，阅读全部输出并确认退出状态。以前运行过、只运行了一个子集、另一个 Agent 说通过、或者代码看起来没问题，都不能替代当前验证。

随后，finishing-a-development-branch 会再次验证测试，并让用户选择如何处理当前工作：本地合并、推送并创建 PR、保留分支，或者在明确确认后丢弃。

| 计划 | writing-plans | 把设计拆成精确、可测试、可评审的实施任务 |

| 并行协作 | dispatching-parallel-agents | 将彼此独立的问题并行交给多个 Agent |
| 测试 | test-driven-development | 执行 RED-GREEN-REFACTOR |

## 用“登录限流”完整走一遍流程

回到文章开头的需求：

> 给登录接口加一个限流功能。

下面用一个简化示例看看 Superpowers 会怎样改变执行过程。

### 1. 不立刻修改代码，先澄清约束

Agent 会先读取项目结构和现有认证逻辑，然后一次讨论一个关键问题，例如：

- 限流目标是防止单账号暴力破解，还是防止单个 IP 扫描大量账号？
- 服务是否多实例部署，当前是否已有 Redis？
- 只统计失败请求，还是所有登录请求？
- 限制触发后多久恢复？
- Redis 故障时希望安全优先还是可用性优先？

假设最终确认的需求是：

- 按“账号 + 客户端 IP”组合限流；
- 5 分钟内连续失败 5 次后，阻止后续登录尝试 15 分钟；
- 多实例共享 Redis；
- 成功登录后清除失败计数；
- 触发限制时返回 429 和 Retry-After；
- Redis 故障时记录告警并拒绝登录，避免保护失效。

这时，Agent 和用户讨论的已经不再是一个模糊的“加限流”，而是一组可以设计和验证的行为。

### 2. 比较方案，而不是默认选择第一个实现

Agent 可以提出几种方案：

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 进程内 Map | 实现简单，无外部依赖 | 多实例不共享，重启后状态丢失 |
| Redis 固定窗口 | 结构简单，容易使用原子计数 | 窗口边界可能出现突发请求 |
| Redis 滑动窗口或有序集合 | 行为更精确，可记录失败时间 | 操作和清理逻辑更复杂 |

结合已经确认的多实例部署和安全要求，最终选择 Redis 有序集合记录 5 分钟内的失败时间，并使用单独的封禁 Key 保存 15 分钟封禁状态。计数、清理过期记录和触发封禁通过 Lua 脚本保持原子性；账号先做规范化和不可逆摘要，再参与 Key 计算，避免直接暴露身份信息。

### 3. 写出精确实施计划

计划不会只写“实现限流并添加测试”。下面假设这是一个 Node.js 项目，并为篇幅展示计划摘要；真实的 writing-plans 产物还会写出完整代码片段、每一步的期望输出和提交动作。

```text
任务 1：新增 LoginAttemptLimiter 接口及 Redis 实现
  - 文件：src/auth/login-attempt-limiter.ts
  - 测试：tests/auth/login-attempt-limiter.test.ts
  - 写失败测试：记录第 5 次失败后，下一次检查返回 blocked 状态
  - 运行：npm test -- tests/auth/login-attempt-limiter.test.ts
  - 预期：FAIL，提示 LoginAttemptLimiter 尚未实现
  - 实现最小 Redis 操作
  - 重新运行同一测试，预期 PASS

任务 2：把限流器接入登录服务
  - 文件：src/auth/login-service.ts
  - 测试：tests/auth/login-service.test.ts
  - 写失败测试：被限制时不再校验密码
  - 写失败测试：成功登录清除失败计数
  - 实现最小接入代码
  - 运行：npm test -- tests/auth

任务 3：增加 HTTP 429 响应和 Retry-After
  - 文件：src/http/login-controller.ts
  - 测试：tests/http/login-controller.test.ts
  - 写接口测试
  - 实现响应映射
  - 运行接口测试、Lint 和构建
```

每个任务都有清楚的边界、测试和验证命令，后续执行 Agent 不需要重新猜测设计。

### 4. 先证明测试能够失败

例如，Agent 先添加一个行为测试：

```javascript
it('blocks login after five failed attempts within five minutes', async () => {
  clock.set('2026-07-13T10:00:00Z');
  await failLogin({ account: 'alice', ip: '203.0.113.8' }, 5);

  const result = await login({
    account: 'alice',
    password: 'wrong-password',
    ip: '203.0.113.8'
  });

  expect(result.status).toBe('rate_limited');
  expect(result.retryAfterSeconds).toBe(900);
});
```

然后实际运行测试，确认它因为限流行为尚未实现而失败。只有这一步成立，测试才有资格进入后续的 GREEN 阶段。

这段代码只演示“累计 5 次失败后阻止后续请求”这一个行为。完整测试还应覆盖 5 分钟统计窗口、15 分钟到期恢复、成功登录清零、不同账号与 IP 组合相互隔离、Redis 故障策略，以及并发请求下的原子性。

### 5. 每个任务使用独立实现与评审循环

如果宿主支持子 Agent，主 Agent 可以把“Redis 限流器”“认证服务接入”“HTTP 响应”按计划逐个交给不同的任务 Agent。每个 Agent 获得当前任务、接口约束和必要项目上下文，而不是继承一整个长会话中的所有噪声。

任务完成后，评审 Agent 先检查：

- 是否确实在累计 5 次失败后才限制后续尝试；
- 成功登录是否清除了状态；
- 不同账号和 IP 是否隔离；
- 是否错误地记录了明文账号或密码；
- Redis 操作是否存在竞态；
- 是否实现了计划之外的复杂策略。
- 发现问题后先修复并重新评审，不能用“总体上差不多”直接放行。

### 6. 最后用完整命令证明结果

在宣布完成之前，Agent 需要运行项目实际使用的验证命令，例如：

```bash
npm test
npm run lint
npm run typecheck
npm run build
```

它必须根据真实输出报告：哪些命令通过、执行了多少测试、是否仍有警告或已知问题。到这一步，“完成”才从一种主观判断变成有证据支持的工程结论。

## 为什么这套方法可能有效

Superpowers 的价值不是来自某个神奇提示词，而是来自几种工程机制的叠加。

### 1. 把隐性经验变成显式步骤

资深工程师往往知道“先确认边界”“先复现再修”“合并前再跑一次完整测试”，但这些习惯容易被默认成常识。

对 Agent 来说，常识如果没有进入当前上下文，就不一定会稳定执行。Skills 把这些经验写成明确的触发条件、步骤和检查表，使它们更容易被重复调用。

### 2. 用阶段门槛阻止错误过早扩散

需求误解如果在写代码前被发现，修正成本可能只是几轮对话；如果等到接口、数据库和测试全部写完才发现，返工成本会高得多。

设计确认、计划评审、失败测试、任务评审和最终验证，都是把问题尽量拦在当前阶段的质量门槛。

### 3. 把大任务变成短反馈循环

计划将长任务拆成多个能够独立测试的单元。每个单元都经历实现、验证和评审，失败时能够更快定位到具体变化，而不是在几十个文件同时修改后才发现整体不可用。

### 4. 用外部反馈纠正模型自信

测试输出、编译器、类型系统、Lint、Git Diff 和独立评审，都属于模型之外的反馈源。它们不能保证需求一定正确，但能减少 Agent 只依赖自身语言判断的情况。

### 5. 分离生产和评价

实现 Agent 负责完成一个任务，评审 Agent 重新从规格和代码质量角度检查结果。虽然两个 Agent 仍可能使用相同模型，但新的上下文和不同角色能够减少“沿着原有实现思路自我证明”的偏差。

### 6. 让失败过程可以复盘

设计、计划、任务报告、测试结果和评审结论构成了一条可追踪链路。任务失败时，团队更容易判断问题发生在需求、设计、实现、测试还是验证阶段，而不是只看到最终的一段错误代码。

## Superpowers 与相邻概念有什么区别

| 概念 | 主要回答的问题 | 与 Superpowers 的关系 |
| --- | --- | --- |
| Prompt Engineering | 这一轮应该怎样描述任务 | Prompt 是局部指令，Superpowers 组织跨阶段流程 |
| Context Engineering | 当前推理应该给模型哪些信息 | Superpowers 会规定何时读取、裁剪和交接上下文 |
| AGENTS.md / 项目规则 | 这个仓库有哪些本地约定 | 项目规则提供事实，Superpowers 提供通用开发方法 |
| MCP / Tool Calling | Agent 能连接和执行什么 | 工具扩展行动能力，Superpowers 约束行动方式 |
| Coding Agent Harness | Agent 如何运行、调用工具和管理循环 | Superpowers 作为技能和方法运行在 Harness 之上 |
| CI/CD | 哪些自动检查决定代码能否进入后续阶段 | Superpowers 应调用并尊重 CI 所代表的客观门槛 |
| 普通 Skill | 某类任务的一份专项操作指南 | Superpowers 是多项 Skills 组成的完整方法体系 |

其中最容易混淆的是 AGENTS.md 和 Superpowers。

AGENTS.md 往往告诉 Agent：项目使用什么框架、目录怎样组织、应该运行哪些命令、哪些文件不能修改。它描述的是这个项目的事实和规则。

Superpowers 告诉 Agent：遇到功能需求时先做什么、怎样把设计变成计划、失败后如何调查、完成前如何验证。它描述的是跨项目复用的工作方法。

两者不是替代关系。理想状态是：Superpowers 提供流程，项目文档提供局部知识，测试和 CI 提供客观反馈。

## 它没有解决什么

一套更完整的流程并不等于没有风险。使用 Superpowers 时，至少要看清下面这些边界。

### 1. 不能修正错误的业务目标

如果用户确认的需求本身就是错的，Agent 可能非常规范地实现错误需求。Brainstorming 能帮助暴露假设，但不能替业务负责人决定产品方向。

### 2. 不能让低质量测试变成高质量证明

测试全部通过，只能说明代码满足了这些测试表达的条件。如果测试遗漏竞态、安全边界、真实依赖或部署差异，绿色结果仍然可能是假安全感。

### 3. 不能完全消除模型不遵守指令的概率

Skills 本质上仍需要模型理解并遵守。强硬措辞、检查表和宿主集成能够提高一致性，但它们不等同于编译器级别的强制执行。

真正不可越过的权限、数据范围和发布门槛，仍然应该由沙箱、鉴权、代码所有者规则和 CI 实现。

### 4. 会增加时间、Token 和调用成本

澄清需求、编写文档、派发子 Agent、进行多轮评审和重复验证都会增加成本。对复杂功能，这些成本可能换来更少返工；对一行文案或明确的机械修改，完整流程可能显得很重。

这也是 Superpowers 一个鲜明的取舍：它优先降低漏项和错误完成的概率，而不是追求第一次看到代码的速度。

### 5. 严格 TDD 并不适合所有产物

当前官方 Skill 默认要求功能、Bug 修复、重构和行为变更执行 TDD，同时把一次性原型、生成代码和配置文件列为需要人类批准的例外。

对于缺少测试基础的遗留系统、纯视觉探索或研究性实验，团队可能需要定义适合自己的边界。但如果自行弱化规则，就应该明确这是团队对方法论的调整，而不是声称仍在完整执行默认流程。

### 6. 子 Agent 和 Worktree 依赖宿主条件

没有子 Agent 能力时，仍然可以使用 executing-plans，但上下文隔离和独立评审的效果会变弱。没有 Git 仓库、测试命令或可复现环境时，部分工作流也无法发挥完整价值。

### 7. 第三方 Skill 需要像代码一样审查

Skill 会影响 Agent 的决策，有些插件还可能附带脚本和运行时集成。安装、升级或引入自定义 Skill 前，应检查来源、内容、执行权限和网络行为，不要因为它表现为 Markdown 就默认没有供应链风险。

官方 README 还说明，Brainstorming 的可选 Visual Companion 默认会从项目网站加载带版本号的品牌图片，用于粗略统计版本使用情况；它不包含项目、Prompt 或点击信息，并可通过 SUPERPOWERS_DISABLE_TELEMETRY 等环境变量关闭。对网络访问敏感的团队应在引入前确认这类默认行为。

## 哪些场景更适合使用

Superpowers 更适合这些任务：

- 涉及多个文件或多个模块的新功能；
- 线上 Bug、间歇性失败和难以定位的测试问题；
- 有明确行为约束、容易产生回归的重构；
- 认证、支付、权限、数据迁移等高风险模块；
- 需要多个 Agent 分工并希望保留评审链路的长任务；
- 希望把团队工程习惯沉淀为可复用流程的项目。

下面这些任务可能会感受到较明显的流程成本：

- 一次性探索原型；
- 纯配置或生成文件修改；
- 非常明确的文案、注释和格式调整；
- 当前根本没有可运行测试或可复现环境的仓库；
- 需求仍处于发散研究阶段、尚不准备进入正式实施的实验。

“任务简单”不等于可以虚构完成结果。即使团队决定对小任务采用更轻量的流程，最终验证仍然应该与风险相匹配。

在 Codex App 侧边栏打开 Plugins，搜索 Superpowers，点击旁边的 + 并按提示安装。当前 v6.1.1 插件清单将它归在 Developer Tools 分类。

### Codex CLI

打开插件搜索界面：

```text
/plugins
```

搜索 superpowers，然后选择 Install Plugin。

### Claude Code

Superpowers 已进入 Claude 官方插件市场，可以执行：

```text
/plugin install superpowers@claude-plugins-official
```

### Cursor

可以在 Cursor Agent 对话中执行：

```text
/add-plugin superpowers
```

也可以直接在插件市场搜索 superpowers。

官方 README 当前还列出了 Antigravity、Factory Droid、GitHub Copilot CLI、Kimi Code、OpenCode 和 Pi 等宿主。一个容易忽略的规则是：如果同时使用多个宿主，需要分别安装，不能假设在一个工具中安装后其他工具会自动共享。

安装后可以像平常一样提出任务。例如：

> 为当前项目增加密码重置功能。

如果技能被正确发现，Agent 通常不会马上开始修改代码，而会先检查项目上下文、澄清设计并进入对应工作流。你也可以明确点名某个 Skill，例如要求使用 systematic-debugging 调查一个间歇性失败。

## 团队如何稳妥引入 Superpowers

如果要在团队中使用，比较稳妥的做法不是一次性把所有任务交给它，而是进行一次有指标的试点。

### 1. 选择一个中等复杂度任务

任务应该包含真实设计取舍、多个文件和可运行测试，但不要一开始就选择最关键的生产迁移。这样既能观察完整流程，也能控制失败成本。

### 2. 先审查 Skills 和插件内容

确认它会读取什么、写入什么、执行哪些脚本、是否访问网络，以及当前版本与团队安全政策是否兼容。

### 3. 与项目规则对齐

把构建命令、测试分层、目录边界、提交规范和安全要求写入 AGENTS.md 或等效项目文档。通用工作流不知道你的业务事实，必须由仓库提供可靠上下文。

### 4. 明确例外由谁批准

例如哪些任务可以不执行 TDD、什么情况下不用 Worktree、哪些命令需要人工确认、哪些目录禁止 Agent 修改。例外应该是团队决策，而不是 Agent 在执行中自行放宽。

### 5. 记录版本并审查升级

Skill 内容的变化会改变 Agent 行为。团队应记录使用版本，阅读 Release Notes，并像升级 Linter、构建插件或 CI Action 一样评估重要变更。

### 6. 用结果而不是感受判断价值

可以比较引入前后的指标：

- 需求澄清后发生的返工次数；
- Code Review 中发现的重要问题数量；
- 逃逸到主分支或生产环境的缺陷；
- 完整任务周期，而不只是首次生成代码的时间；
- 测试和验证覆盖情况；
- Token、模型调用和人工等待成本；
- 长任务中断后能否恢复并继续执行。

如果缺陷和返工没有下降，只是文档和调用次数增加，就需要重新检查 Skill 是否适合当前项目，而不是把“流程更长”本身当作成功。

## 常见问题

### Superpowers 会让模型写代码的能力变强吗？

不会直接提高基础模型能力。它更可能提高的是执行一致性、需求完整性和验证纪律。模型能力决定它能不能理解复杂代码，流程决定它会不会在正确的时间使用这种能力。

### 它只是把软件工程书写成 Prompt 吗？

底层确实依赖自然语言指令，但它不只是单段 Prompt。它还有任务触发、Skill 组合、文档产物、阶段门槛、子 Agent 交接、评审循环和验证证据。更准确地说，它把一部分软件工程方法编码成了 Agent 可执行的流程。

### 它和 MCP 能一起使用吗？

可以。MCP 给 Agent 提供工具和数据，Superpowers 规定怎样使用这些能力完成开发。例如，Agent 可以通过 MCP 查询工单，再使用 Brainstorming 澄清需求，按计划修改代码，最后运行测试验证。

### 它能替代 AGENTS.md 吗？

不能。AGENTS.md 保存项目特有规则，Superpowers 提供跨项目方法。缺少项目文档时，Agent 仍可能按照一套规范流程做出不符合仓库约定的修改。

### 使用后就不会出现幻觉和错误代码了吗？

不会。它能降低没有调查、没有测试、没有评审、没有验证就交付的概率，但不能消除模型误解、错误测试、依赖差异和未知业务约束。

### 所有任务都必须走完全部流程吗？

不是每个任务都需要所有 Skills，但 Superpowers 的默认立场很严格：只要某个 Skill 适用，就应该执行。尤其是功能开发前的设计和实现阶段的 TDD，当前版本都设置了明确门槛。团队可以定义例外，但应该由人明确批准。

### 没有子 Agent 还能用吗？

可以。需求澄清、计划、TDD、系统化调试和完成验证仍然有价值。只是不能获得“每个任务使用干净上下文”和“实现、评审角色分离”的完整效果，可以改用 executing-plans 顺序执行。

### 如何判断它有没有真正解决问题？

不要只看 Agent 是否写了更多文档，也不要只看第一次输出代码是否更慢。应该观察最终返工、缺陷、评审问题、任务恢复能力和总成本是否改善。

## 总结

理解 Superpowers，可以记住下面四句话：

- 它不是新的模型，而是一套运行在 Coding Agent 之上的技能框架和软件开发方法论。
- 它解决的重点不是“模型不会写代码”，而是“模型不稳定地遵守可靠开发流程”。
- 它通过需求澄清、计划拆分、TDD、根因调试、独立评审和完成验证，把工程纪律变成可执行步骤。
- 它能降低流程失控和虚假完成的概率，但不能替代正确需求、高质量测试、权限边界、CI 和人工判断。

Superpowers 最有价值的地方，不是让 AI 突然拥有“超能力”，而是提醒我们一个很朴素的工程事实：

模型能力决定上限，工程流程决定这个上限能否被稳定地兑现。
