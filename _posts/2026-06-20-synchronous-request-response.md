用户点一个按钮，前端发一个 HTTP 请求，后端处理完直接把结果返回；服务之间也一样，A 服务调 B 服务的接口，发出请求后一直等，直到 B 返回结果或者超时才继续往下走。这种一问一答、原地等结果的方式就是同步请求-响应，也是后端里最常见的交互方式。

它的模型很简单，但要在生产环境跑稳并不容易。下游会变慢、会超时、会挂，调用方如果不设防，很容易被一起拖垮。

<!--more-->

```text
调用方发出请求
  -> 阻塞等待
  -> 被调用方处理
  -> 返回结果
  -> 调用方拿到结果继续执行
```

上了生产以后，常见的麻烦有这些：

- 下游变慢，请求线程和连接被长时间挂住。
- 下游偶发超时，要不要重试？重试会不会把请求做两遍？
- 高峰期大量请求打到一个慢下游，线程池被打满，不相关的接口也跟着挂。
- 网络抖动，请求其实已经成功，调用方没收到响应，以为失败了。
- 一个下游故障沿调用链一路放大，最后整个系统雪崩。

所以要解决的问题是：下游不可靠时，怎么让这条同步链路不被拖垮。

## 什么时候该用同步

最典型的是延迟敏感、用户在屏幕前等结果的场景：登录鉴权、查询余额和订单详情、商品详情页、搜索结果页、后台管理系统的增删改查。用户要的就是点一下立刻有反应，不能回一句"任务已受理，请稍后查询"。

其次是服务间的强依赖调用，比如下单前校验库存、支付前查询账户状态、网关调鉴权服务校验 token，拿不到结果业务就走不下去。需要强一致语义的场景也一样，数据库读写（SQL 查询本身就是同步请求-响应）、分布式事务里各参与方的同步确认，异步化会把强一致变成最终一致，这类场景不接受。另外，内部工具、运维脚本、定时任务拉数据这类简单低并发的调用，没有削峰、解耦的需求，同步实现成本最低，没必要引入队列。

反过来，下面这些场景就不该硬用同步：

- 耗时长：视频转码、报表生成、AI 内容生成。同步会长时间占用连接和线程，应改成异步任务。
- 需要削峰填谷：瞬时大流量直接打到下游会被压垮，需要 MQ 缓冲。
- 多方广播、解耦：一份事件要通知很多消费者，应该用发布订阅。
- 下游慢且可容忍延迟：异步重试比同步死等更可靠。

我的判断标准是：用户必须当场拿到结果、耗时又可控，就用同步；可以晚点拿结果，或者耗时不可控，就走异步任务。

## 一次稳定的调用要经过哪些环节

有几条底线：调用方永远不无限等待，超时是底线；重试必须配合幂等，否则会把请求做多遍；故障要能快速隔离，不让一个下游拖垮全局；失败要有兜底，能降级就不硬失败。

落到一次调用上，就不只是"发请求、收响应"两步：

```text
调用方发起请求
  -> 限流：判断是否超过自身承载能力
  -> 熔断：判断下游当前是否健康
  -> 从连接池取连接
  -> 带超时发起调用
       成功：返回结果
       超时/失败：判断是否可重试
            可重试且幂等：退避后重试
            不可重试或重试耗尽：走降级兜底
  -> 释放连接
  -> 记录链路、指标、日志
```

同步调用的稳定性靠的不是下游永远可靠，而是调用方自己把超时、熔断、隔离和降级做好。任何一次调用都要假设它可能慢、可能失败，也可能超时了其实已经成功。

按阶段拆开看是这样：

```text
准入 -> 获取连接 -> 发送请求 -> 等待响应 -> 处理结果 -> 释放资源
                                      |
                                   失败/超时
                                      |
                              重试 -> 重新发送
                                      |
                                重试耗尽 -> 降级
```

每个阶段都对应一种防护：准入靠限流熔断，获取连接靠连接池，等待响应靠超时，处理结果靠错误分类，失败后靠重试和降级，最后释放资源时要防止连接泄漏。

## 接口契约

契约没定清楚，后面的超时、重试、幂等都会很别扭。

### 超时预算

每个接口都要有自己的超时预算，不要全用一个全局默认值。大致可以参考：查询类接口 200ms ~ 500ms，普通写接口 500ms ~ 1s，复杂聚合接口 1s ~ 3s。调用方和被调用方要对超时有共识，被调用方如果知道自己经常需要 2 秒，就不应该让调用方按 500ms 超时。

### 响应结构与错误码

响应里要能区分"成功""业务失败""系统错误"，调用方才能决定要不要重试。

```json
{
  "code": 0,
  "message": "ok",
  "data": { }
}
```

错误码最好能表达可重试性：

| code 类别 | 含义 | 调用方应对 |
| --- | --- | --- |
| 成功 | 业务成功 | 直接用结果 |
| 业务错误 | 参数错、余额不足 | 不重试，直接返回 |
| 系统错误 | 下游异常、超时 | 可重试 |
| 限流/熔断 | 暂时不可用 | 退避后重试或降级 |

**业务失败和系统错误一定要分开。** 业务失败重试没有意义，很多重试风暴就是因为把所有失败都当成了可重试。

### 幂等键与批量接口

允许调用方重试的写接口，要在契约里明确幂等键怎么传（具体做法见下面的"幂等"一节），统一约定，别让每个调用方各自发挥。为了减少往返，契约里也可以直接提供批量接口，比如用一次 `POST /users/batch` 传 100 个 id，代替循环调用 100 次 `GET /user/{id}`。

## 技术选型

RPC 框架、连接池、缓存、熔断限流组件、网关都可能用到，但不是每个业务都要全上。

### 通信协议与框架

| 类别 | 代表技术 | 适合场景 |
| --- | --- | --- |
| HTTP/REST | Spring MVC、FastAPI、Express | 通用、对外开放、跨语言 |
| RPC | gRPC、Dubbo、Thrift | 服务间高性能强类型调用 |
| GraphQL | Apollo | 客户端按需查询，减少往返 |
| 数据库协议 | JDBC、MySQL 协议 | SQL 查询本质就是同步请求-响应 |

对外、跨团队、要可读性，用 HTTP/REST；内部服务间追求性能和强类型，用 gRPC 或 Dubbo；前端字段需求多变、想减少接口数量，可以考虑 GraphQL。

### 连接池

连接池几乎是必须的。每次调用都新建 TCP 连接开销很大，连接池可以复用连接，避免反复握手。要关注最大连接数（太小会排队，太大会压垮下游），连接超时和获取连接超时分开设置，空闲连接要回收，避免连接老化。常见实现：数据库用 HikariCP，HTTP 用 Apache HttpClient / OkHttp 连接池，gRPC 复用 Channel。

### 缓存

缓存是同步调用最有效的优化手段之一。同一个请求的结果短期内不变，就可以用本地缓存或 Redis 挡住重复调用：

```text
请求进来
  -> 先查缓存
       命中：直接返回，不调下游
       未命中：调下游，回填缓存
```

读多写少、结果短期内不变、下游较慢或较贵时适合缓存；强一致读必须拿最新值，或者数据频繁变化、命中率低时，就不能只靠缓存。

### 熔断限流与网关

跨服务的同步调用，建议都配上熔断和限流。常用组件里，Resilience4j 比较轻量，熔断、限流、重试、舱壁都有；Sentinel 支持限流、熔断和热点参数限流，控制台完善；Hystrix 是老牌的熔断隔离组件，已停止维护。单机内部调用、下游很稳定时可以先不上熔断，一旦涉及不稳定的第三方依赖，熔断和限流就应该补上。

对外的同步接口通常还会经过网关，统一做鉴权、限流、超时、日志。网关的超时一定要和后端接口的超时预算对齐，否则会出现"后端还在跑，网关已经超时返回"的情况。

## 幂等

只要接口允许重试，就必须考虑幂等。查询类接口天然幂等，可以放心重试；写接口要靠幂等键保证多次调用只生效一次，调用方带上幂等键：

```http
POST /api/orders
Idempotency-Key: order:user123:cart456
```

被调用方用幂等键做唯一约束或去重表：

```sql
CREATE TABLE idempotent_record (
  idempotency_key VARCHAR(128) NOT NULL,
  result_payload JSON NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (idempotency_key)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

处理逻辑：

```text
收到请求
  -> 用幂等键查去重表
       已存在：直接返回上次的结果，不再执行
       不存在：执行业务，保存结果和幂等键
```

这样调用方重试多少次，真正的业务都只执行一次。

### 超时了，但其实成功了

同步调用里最隐蔽的问题是：请求其实已经成功，但调用方因为超时没收到响应，以为失败了。

```text
调用方发请求
  -> 下游处理成功，扣了款
  -> 返回响应时网络抖动
  -> 调用方读取超时，认为失败
  -> 调用方重试
  -> 如果没有幂等，就会扣两次款
```

**超时不等于失败。** 只要可能重试，写接口就必须幂等，这是同步调用里最容易踩的坑。关键操作还可以额外提供一个"查询结果"接口，调用方拿不准的时候先查一下，再决定要不要重试。

## 超时与连接池隔离

### 永远要设超时

没有超时的同步调用最危险。下游一旦卡住，调用方线程就一直挂着，连接池很快被占满，最后整个服务不可用。连接超时、读取超时、从连接池获取连接的超时要分别设置：

```text
connectTimeout = 1s
readTimeout = 2s
poolAcquireTimeout = 500ms
```

### 超时预算沿调用链传递

一条请求可能经过多层服务：网关 -> A -> B -> C。如果每层都设 3 秒，最外层用户可能要等 9 秒。更合理的做法是把超时预算往下传，剩余时间不够就直接快速失败，不再往下调：

```text
入口预算 3s
  -> A 用掉 500ms，传给 B 剩 2.5s
  -> B 用掉 1s，传给 C 剩 1.5s
  -> C 必须在 1.5s 内返回
```

### 连接池按下游隔离

不同下游不要共用一个连接池。如果库存、风控、优惠券共用一个连接池，优惠券变慢把连接占光，库存和风控也跟着没连接用。给每个下游分配独立连接池，就是舱壁隔离。

## 重试、熔断与降级

### 什么失败值得重试

失败以后先判断该不该重试：

```text
可重试：
  连接超时、读取超时
  下游 5xx、限流、临时不可用

不可重试：
  参数错误、业务校验失败
  权限不足、资源不存在
```

只有系统性、瞬时性的失败才值得重试，业务失败重试只会增加无效流量。

重试也不能立即、无限地重试，否则会形成重试风暴，把本来就在挣扎的下游彻底打垮。要做退避：

```text
第 1 次失败：等 100ms 重试
第 2 次失败：等 200ms 重试
第 3 次失败：等 400ms 重试
超过次数：放弃，走降级
```

退避之外还要加随机抖动，避免大量调用方同时重试。另外再强调一次，没有幂等的写接口，不要随意开重试。

### 熔断与降级

下游持续失败时，继续重试只是浪费资源。熔断器在失败率超过阈值后打开，后续请求直接快速失败或走降级，给下游留出恢复时间。它有三种状态：关闭时正常调用；打开时直接快速失败，不再真正调用；半开时放少量请求试探下游是否恢复。

熔断打开或重试耗尽后，尽量给个兜底，别直接给用户报错：返回缓存里的旧数据、返回一个默认值，或者提示"部分功能暂不可用"但不影响主流程。目标是保住核心可用性，别因为一个下游挂了整个页面都打不开。

## 性能优化

多个无依赖的下游，不要串行调，要并行：

```text
串行：A(80ms) -> B(80ms) -> C(80ms) = 240ms
并行：max(A, B, C) = 80ms
```

用 CompletableFuture、Promise.all 或协程并发发起，再聚合结果，总耗时就从三者之和降到三者中的最大值。

多次小请求可以合并成一次批量请求，减少网络往返：

```text
不要：for id in ids: GET /user/{id}
而是：POST /users/batch  body: { ids: [...] }
```

其他几个常用手段：热点数据放本地缓存或 Redis，挡掉大量重复调用，注意缓存一致性和过期策略；gRPC 用 Protobuf + HTTP/2 多路复用，比 JSON over HTTP/1.1 更省带宽和连接；大响应体可以压缩，只返回需要的字段；调用链越长，累计延迟和故障概率越大，能合并的服务调用就合并，能在一层解决的就不要层层转发。

## 故障与容错

前面这些手段都是为了不让局部故障演变成全局雪崩：严格超时和连接池隔离防止慢下游拖垮调用方，舱壁隔离、熔断降级和每一层的限流挡住故障沿调用链放大，幂等加去重表兜住重试带来的重复执行。

还有一种情况前面没提到：并行调用多个下游时，部分成功、部分失败。这时要先分清哪些是核心依赖、哪些是非核心，非核心失败可以降级，核心失败才整体失败，必要时对已经成功的操作做补偿回滚。

## 落地流程

把上面的内容串起来，一次同步调用大致是这样：

1. 发起前：限流判断，超过自身承载就拒绝或排队；熔断判断，下游不健康就直接走降级；写操作准备幂等键；计算本次调用的超时预算。
2. 发起调用：从对应下游的独立连接池获取连接，带连接超时和读取超时发起请求，等待响应。
3. 处理结果：成功就解析结果，必要时回填缓存后返回；业务失败不重试，直接返回错误；系统失败或超时，可重试且幂等就退避加抖动后重试，重试耗尽走降级兜底。
4. 收尾：释放连接，记录链路 TraceId、耗时、错误率。

如果要并行调用多个下游，无依赖的并发发起、各自带独立超时，再聚合结果；核心下游失败则整体失败，非核心失败则降级。

## 常见误区

不设超时、所有失败都重试、重试不配幂等、所有下游共用一个连接池或线程池、无依赖的下游串行调用、每层超时层层叠加，这些坑前面都讲过。另一个反方向的误区是一上来就堆全套熔断限流。如果只是稳定的内部低频调用，连接池加超时可能就够了，中间件要匹配业务风险。

## 场景题

你在做一个电商的「下单」接口，它是一个同步请求-响应接口，用户点击下单后要当场返回成功或失败。

下单流程中需要同步调用三个下游服务：库存服务（扣减库存）、风控服务（校验用户是否异常）、优惠券服务（核销优惠券）。当前实现是串行同步调用这三个服务，平均每个 80ms，下单接口 P99 约 300ms。

最近大促期间，优惠券服务偶发抖动，响应时间飙到 2 秒甚至超时，结果整个下单接口大面积超时，线程池被打满，连不用优惠券的订单也下不了单。

如果让你重新设计这个同步调用链路，你会怎么做？可以从这几个角度想想：

- 为什么"一个下游抖动"会拖垮"整个下单接口"，根因是什么？
- 在仍然保持同步请求-响应的前提下，你会用哪些手段把 P99 降下来，并防止单个下游故障引发雪崩？
- 三个调用里，哪些必须同步、哪些其实可以异步化？如果改造，要注意什么一致性问题？
- 如果调用优惠券服务超时了，但其实它已经把券核销了，你怎么保证用户不会被重复核销？
