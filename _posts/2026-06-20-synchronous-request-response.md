## 1. 前言

在后端开发里，最常见、最基础的一种交互方式，就是同步请求-响应。

<!--more-->

用户点一个按钮，前端发一个 HTTP 请求，后端处理完直接把结果返回，前端拿到结果再渲染页面。服务之间也是一样，A 服务调用 B 服务的接口，发出请求后一直等，直到 B 返回结果或超时，A 才继续往下执行。

它的形态非常简单：

```text
调用方发出请求
  -> 阻塞等待
  -> 被调用方处理
  -> 返回结果
  -> 调用方拿到结果继续执行
```

请求和响应在一次调用里一一对应，调用方拿到结果才往下走。这种"一问一答、原地等结果"的模式，就是同步请求-响应。

它看起来简单，但真正做稳定并不容易。一旦上了生产，就要面对一堆现实问题：

- 下游服务变慢，请求线程被长时间占用，连接被挂住。
- 下游偶发超时，调用方该不该重试，重试会不会把请求做两遍。
- 高峰期大量请求同时打到一个慢下游，线程池被打满，连不相关的接口也跟着挂。
- 网络抖动，请求其实已经成功，但调用方没收到响应，以为失败了。
- 一个下游故障，沿着调用链一路放大，最后整个系统雪崩。

所以同步请求-响应模式真正的难点，不在于"怎么发请求拿结果"，而在于怎么在下游不可靠的前提下，把这条同步链路做得稳定、可控、不被拖垮。

本文不绑定某个具体框架，而是讲这套模式背后的通用工程实践。

## 2. 适用场景

同步请求-响应适合下面这些场景。

### 2.1 延迟敏感、需要即时反馈

用户在屏幕前等着，必须马上看到结果。

典型例子：

- 登录鉴权
- 查询余额、查询订单详情
- 商品详情页、搜索结果页
- 后台管理系统的增删改查

这类场景用户就是要"点一下立刻有反应"，不能告诉他"任务已受理，请稍后查询"。

### 2.2 服务间的强依赖调用

A 服务必须拿到 B 服务的结果才能继续业务。

比如：

- 下单前同步校验库存是否充足
- 支付前同步查询账户状态
- 网关同步调用鉴权服务校验 token

这些调用是业务往下走的前置条件，天然就是同步的。

### 2.3 需要强一致语义

业务要求"读到的就是最新值""这一步失败整笔回滚"。

比如：

- 数据库读写，SQL 查询本身就是同步请求-响应
- 分布式事务里各参与方的同步确认

异步化会把强一致变成最终一致，这类场景不接受。

### 2.4 简单、低并发的内部调用

内部工具、运维脚本、定时任务拉数据，对削峰、解耦没有特殊要求。

用同步调用实现成本最低，没必要引入队列。

### 2.5 不适合的场景

同步请求-响应不是万能的，下面这些场景就不该硬用同步。

- 耗时长：视频转码、报表生成、AI 内容生成。同步会长时间占用连接和线程，应改成异步任务。
- 需要削峰填谷：瞬时大流量直接打到下游会被压垮，需要 MQ 缓冲。
- 多方广播、解耦：一份事件要通知很多消费者，应该用发布订阅。
- 下游慢且可容忍延迟：异步重试比同步死等更可靠。

一句话判断边界：

- 用户必须当场拿到结果，且耗时可控 -> 同步请求-响应
- 提交完可以晚点拿结果，或耗时不可控 -> 异步任务

## 3. 核心思想

同步请求-响应模式做稳定，核心可以概括为四句话：

- 调用方永远不无限等待，超时是底线。
- 重试必须配合幂等，否则会把请求做多遍。
- 故障要能快速隔离，不让一个下游拖垮全局。
- 失败要有兜底，能降级就不要硬失败。

一个健壮的同步调用，内部其实不止"发请求、收响应"两步，而是这样：

```text
调用方发起请求
  -> 限流：判断是否超过自身承载能力
  -> 熔断：判断下游当前是否健康
  -> 从连接池取连接
  -> 带超时发起调用
       成功：返回结果
       超时/失败：判断是否可重试
            可重试且幂等：退避后重试
            不可重试或重试耗尽：走降级兜底
  -> 释放连接
  -> 记录链路、指标、日志
```

这里最重要的一点是：同步调用的稳定性，不是靠下游永远可靠，而是靠调用方自己做好超时、熔断、隔离和降级。

不要默认下游一定会及时返回。任何一次同步调用，都要假设它可能慢、可能失败、可能超时却其实已经成功。

## 4. 一次调用的生命周期

异步任务有任务状态机，同步调用也有它自己的"生命周期"。把这条链路上的每个阶段看清楚，才知道每个阶段会出什么问题、要加什么防护。

常见阶段：

| 阶段 | 含义 | 主要风险 |
| --- | --- | --- |
| 准入 | 限流、熔断判断是否放行 | 不放行会拒绝请求 |
| 获取连接 | 从连接池拿连接 | 连接池耗尽，等待或失败 |
| 发送请求 | 把请求写到下游 | 连接超时、网络异常 |
| 等待响应 | 阻塞等下游处理 | 读取超时、下游变慢 |
| 处理结果 | 解析响应、判断成败 | 解析异常、业务错误码 |
| 重试或降级 | 失败后的决策 | 重复执行、雪崩 |
| 释放资源 | 归还连接、记录指标 | 连接泄漏 |

基本流转可以是：

```text
准入 -> 获取连接 -> 发送请求 -> 等待响应 -> 处理结果 -> 释放资源
                                      |
                                   失败/超时
                                      |
                              重试 -> 重新发送
                                      |
                                重试耗尽 -> 降级
```

把生命周期画清楚的价值在于：每个阶段都对应一个具体的稳定性手段。准入对应限流熔断，获取连接对应连接池，等待响应对应超时，处理结果对应错误分类，重试降级对应容错。后面的章节就是逐个阶段展开。

## 5. 接口与契约设计

异步任务模式里最重要的是任务表设计，同步请求-响应模式里最重要的是接口契约设计。契约定义不清，后面所有的超时、重试、幂等都会很别扭。

一个清晰的同步接口契约，应该约定下面这些东西。

### 5.1 明确的超时预算

每个接口都要有自己的超时预算，而不是用一个全局默认值。

- 查询类接口：200ms ~ 500ms
- 普通写接口：500ms ~ 1s
- 复杂聚合接口：1s ~ 3s

调用方和被调用方要对超时有共识。被调用方如果知道自己经常需要 2 秒，就不应该让调用方按 500ms 超时。

### 5.2 统一的响应结构

响应里要能区分"成功""业务失败""系统错误"，这样调用方才能正确决定是否重试。

```json
{
  "code": 0,
  "message": "ok",
  "data": { }
}
```

错误码设计要能表达可重试性：

| code 类别 | 含义 | 调用方应对 |
| --- | --- | --- |
| 成功 | 业务成功 | 直接用结果 |
| 业务错误 | 参数错、余额不足 | 不重试，直接返回 |
| 系统错误 | 下游异常、超时 | 可重试 |
| 限流/熔断 | 暂时不可用 | 退避后重试或降级 |

把"业务失败"和"系统错误"分开非常关键。业务失败重试没有意义，系统错误才值得重试。很多重试风暴就是因为把所有失败都当成可重试。

### 5.3 幂等约定

如果接口允许调用方重试，就必须约定幂等键的传递方式。

```http
POST /api/orders
Idempotency-Key: order:user123:cart456
```

把幂等键作为契约的一部分明确下来，而不是让每个调用方各自发挥。

### 5.4 分页与批量

为了减少往返次数，契约里可以提供批量接口。

```text
不要：循环调用 100 次 GET /user/{id}
而是：一次调用 POST /users/batch  传 100 个 id
```

这是同步调用性能优化的基础，放在契约层面统一约定。

## 6. 中间件与技术选型取舍

同步请求-响应可能涉及 RPC 框架、连接池、缓存、熔断限流组件、网关等，但不是每个业务都要全上。

### 6.1 通信协议与框架

| 类别 | 代表技术 | 适合场景 |
| --- | --- | --- |
| HTTP/REST | Spring MVC、FastAPI、Express | 通用、对外开放、跨语言 |
| RPC | gRPC、Dubbo、Thrift | 服务间高性能强类型调用 |
| GraphQL | Apollo | 客户端按需查询，减少往返 |
| 数据库协议 | JDBC、MySQL 协议 | SQL 查询本质就是同步请求-响应 |

选型建议：

- 对外、跨团队、要可读性，用 HTTP/REST。
- 内部服务间、追求性能和强类型，用 gRPC 或 Dubbo。
- 前端字段需求多变、想减少接口数量，考虑 GraphQL。

### 6.2 连接池

连接池几乎是必须的。

每次同步调用都新建 TCP 连接，开销很大。连接池可以复用连接，避免反复握手。

适合关注的点：

- 最大连接数：太小会排队，太大会压垮下游。
- 连接超时和获取连接超时要分开设置。
- 空闲连接回收，避免连接老化。

常见实现：数据库用 HikariCP，HTTP 用 Apache HttpClient / OkHttp 连接池，gRPC 复用 Channel。

### 6.3 缓存

缓存是同步调用最有效的优化手段之一。

如果同一个请求结果短期内不变，可以用本地缓存或 Redis 挡住重复调用。

```text
请求进来
  -> 先查缓存
       命中：直接返回，不调下游
       未命中：调下游，回填缓存
```

适合缓存的情况：

- 读多写少。
- 结果短期内不变。
- 下游较慢或较贵。

不适合只靠缓存的情况：

- 强一致读，必须拿最新值。
- 数据频繁变化，缓存命中率低。

### 6.4 熔断限流组件

只要是跨服务的同步调用，就建议配熔断和限流。

| 组件 | 能力 |
| --- | --- |
| Resilience4j | 熔断、限流、重试、舱壁，轻量 |
| Sentinel | 限流、熔断、热点参数限流，控制台完善 |
| Hystrix | 老牌熔断隔离，已停止维护 |

如果只是单机内部调用、下游很稳定，可以先不上熔断。一旦涉及不稳定的第三方依赖，熔断和限流就应该补上。

### 6.5 网关

对外的同步接口，通常会经过网关统一做鉴权、限流、超时、日志。

网关层的超时一定要和后端接口的超时预算对齐，否则会出现"后端还在跑，网关已经超时返回"的割裂。

## 7. 幂等设计

同步请求-响应模式里，幂等同样重要。只要接口允许重试，就必须考虑幂等。

幂等要解决两个问题：

- 调用方重试时，不能把同一个操作执行两遍。
- 网络抖动导致响应丢失、调用方以为失败重发时，下游不能重复处理。

### 7.1 读接口天然幂等

查询类接口多次调用结果一致，天然幂等，可以放心重试。

### 7.2 写接口要靠幂等键

写接口要靠幂等键保证多次调用只生效一次。

调用方带上幂等键：

```http
POST /api/orders
Idempotency-Key: order:user123:cart456
```

被调用方用幂等键做唯一约束或去重表：

```sql
CREATE TABLE idempotent_record (
  idempotency_key VARCHAR(128) NOT NULL,
  result_payload JSON NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (idempotency_key)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

处理逻辑：

```text
收到请求
  -> 用幂等键查去重表
       已存在：直接返回上次的结果，不再执行
       不存在：执行业务，保存结果和幂等键
```

这样即使调用方重试很多次，真正的业务也只执行一次。

### 7.3 超时但其实成功的问题

同步调用最隐蔽的一个问题是：请求其实已经成功，但调用方因为超时没收到响应，以为失败了。

```text
调用方发请求
  -> 下游处理成功，扣了款
  -> 返回响应时网络抖动
  -> 调用方读取超时，认为失败
  -> 调用方重试
  -> 如果没有幂等，就会扣两次款
```

所以"超时"绝不等于"失败"。只要可能重试，写接口就必须幂等。这是同步调用里最容易踩的坑。

## 8. 超时与连接：稳定性的底线

异步任务模式有"可靠投递"问题，同步请求-响应模式对应的核心问题是超时和连接管理。

### 8.1 永远要设超时

没有超时的同步调用是最危险的。下游一旦卡住，调用方线程就一直挂着，连接池很快被占满，最后整个服务不可用。

要分别设置：

- 连接超时：建立连接的最长时间。
- 读取超时：等待响应的最长时间。
- 获取连接池连接的超时：连接池满时等待的最长时间。

```text
connectTimeout = 1s
readTimeout = 2s
poolAcquireTimeout = 500ms
```

### 8.2 超时预算要沿调用链分配

一条请求可能经过多层服务：网关 -> A -> B -> C。

如果每层都设 3 秒，最外层用户可能要等 9 秒。正确做法是做"超时预算传递"，剩余时间不够就直接快速失败，不再往下调。

```text
入口预算 3s
  -> A 用掉 500ms，传给 B 剩 2.5s
  -> B 用掉 1s，传给 C 剩 1.5s
  -> C 必须在 1.5s 内返回
```

### 8.3 连接池要做隔离

不同下游不要共用一个连接池。

如果库存、风控、优惠券共用一个连接池，优惠券变慢把连接占光，库存和风控也跟着没连接用。给每个下游分配独立连接池，就是舱壁隔离。

## 9. 失败处理与重试

同步调用失败后，要先判断该不该重试，再决定怎么重试。

### 9.1 区分可重试与不可重试

```text
可重试：
  连接超时、读取超时
  下游 5xx、限流、临时不可用

不可重试：
  参数错误、业务校验失败
  权限不足、资源不存在
```

业务失败重试没有意义，只会增加无效流量。只有系统性、瞬时性的失败才值得重试。

### 9.2 重试要退避加抖动

重试不能立即且无限重试，否则会形成重试风暴，把本来就在挣扎的下游彻底打垮。

```text
第 1 次失败：等 100ms 重试
第 2 次失败：等 200ms 重试
第 3 次失败：等 400ms 重试
超过次数：放弃，走降级
```

退避之外还要加随机抖动，避免大量调用方同时重试。

### 9.3 重试必须配合幂等

重试的前提是幂等，否则就会重复执行。第 7 节已经讲过，这里强调一遍：没有幂等的写接口，不要随意开重试。

### 9.4 熔断：失败到一定程度就快速失败

如果下游持续失败，继续重试只是浪费资源。熔断器在失败率超过阈值时直接打开，后续请求快速失败或走降级，给下游恢复的时间。

- 关闭：正常调用
- 半开：放少量请求试探下游是否恢复
- 打开：直接快速失败，不再真正调用

### 9.5 降级：失败时给兜底

熔断打开或重试耗尽后，不要直接给用户报错，尽量给兜底：

- 返回缓存里的旧数据。
- 返回一个默认值。
- 返回"部分功能暂不可用"，但不影响主流程。

降级的目标是保住核心可用性，而不是一个下游挂了整个页面打不开。

## 10. 性能优化

异步任务模式关注"查询任务状态"的效率，同步请求-响应模式关注"如何让这次同步调用更快"。

### 10.1 并行调用

多个无依赖的下游，不要串行调，要并行。

```text
串行：A(80ms) -> B(80ms) -> C(80ms) = 240ms
并行：max(A, B, C) = 80ms
```

实现上用 CompletableFuture、Promise.all、协程并发发起，再聚合结果。把"三者之和"降成"三者最大值"。

### 10.2 批量合并

把多次小请求合并成一次批量请求，减少网络往返。

```text
不要：for id in ids: GET /user/{id}
而是：POST /users/batch  body: { ids: [...] }
```

### 10.3 缓存挡量

热点数据放本地缓存或 Redis，能挡掉大量重复的同步调用。注意缓存一致性和过期策略。

### 10.4 协议与序列化优化

- gRPC 用 Protobuf + HTTP/2 多路复用，比 JSON over HTTP/1.1 更省带宽和连接。
- 大响应体可以压缩。
- 只返回需要的字段，避免传输冗余数据。

### 10.5 减少调用层级

调用链越长，累计延迟和故障概率越大。能合并的服务调用合并，能在一层解决的就不要层层转发。

## 11. 故障与容错恢复

同步调用没有"宕机后恢复任务"的问题，但有它自己的容错难题：如何不让局部故障演变成全局雪崩。

常见故障与应对：

### 11.1 下游变慢拖垮调用方

下游响应变慢，调用方线程被大量占用，连接池耗尽，最后自己也不可用。

应对：

- 严格超时，不让请求无限等待。
- 连接池隔离，一个下游慢不影响其他。
- 熔断，下游持续慢就快速失败。

### 11.2 雪崩

一个底层服务故障，沿调用链层层放大，最终整个系统不可用。

应对：

- 舱壁隔离：每个下游独立资源池。
- 熔断降级：及时切断故障传播。
- 限流：保护每一层不被打满。

### 11.3 重复执行

网络抖动导致超时重试，下游被执行多次。

应对：写接口幂等，去重表 + 唯一约束兜底。

### 11.4 超时却成功

调用方以为失败，实际下游已成功。

应对：

- 写操作幂等，重试不会重复生效。
- 关键操作可以提供"查询结果"接口，调用方在不确定时先查询再决定是否重试。

### 11.5 部分失败

并行调用多个下游时，部分成功部分失败。

应对：

- 明确哪些是核心依赖、哪些是非核心。
- 非核心失败可降级，核心失败才整体失败。
- 必要时对已成功的操作做补偿回滚。

## 12. 一个推荐流程

把同步请求-响应的稳定调用整理成一套落地流程。

### 发起调用前

1. 限流判断：超过自身承载就拒绝或排队
2. 熔断判断：下游不健康就直接走降级
3. 准备幂等键（写操作）
4. 计算本次调用的超时预算

### 发起调用

1. 从对应下游的独立连接池获取连接
2. 带连接超时和读取超时发起请求
3. 等待响应

### 处理结果

1. 成功：解析结果，必要时回填缓存，返回
2. 业务失败：不重试，直接返回错误
3. 系统失败/超时：判断是否可重试
    - 可重试且幂等：退避加抖动后重试
    - 重试耗尽：走降级兜底
4. 释放连接
5. 记录链路 TraceId、耗时、错误率

### 并行调用多个下游

1. 无依赖的下游并发发起
2. 各自带独立超时
3. 聚合结果
4. 核心下游失败则整体失败，非核心失败则降级

## 13. 常见误区

### 13.1 不设超时

最危险的错误。下游一卡，调用方线程和连接被占满，自己也跟着挂。任何同步调用都必须有超时。

### 13.2 把所有失败都重试

业务失败重试没意义，还会放大流量。要区分可重试和不可重试，只对系统性瞬时失败重试。

### 13.3 重试不配幂等

重试加非幂等写接口，等于主动制造重复执行。超时不等于失败，重试前必须确保幂等。

### 13.4 所有下游共用一个连接池/线程池

一个下游变慢就会拖垮所有调用。要做舱壁隔离，按下游分池。

### 13.5 串行调用无依赖的下游

明明可以并行，却一个个串着调，延迟白白叠加。无依赖就并行。

### 13.6 超时预算层层叠加

每层都设一样的大超时，导致最外层用户等很久。要做超时预算传递，剩余时间不够就快速失败。

### 13.7 一上来就堆全套熔断限流

如果只是稳定的内部低频调用，连接池加超时可能就够了。中间件要匹配业务风险，而不是堆技术栈。

## 14. 总结

同步请求-响应模式适合延迟敏感、需要即时反馈、强依赖、强一致的场景。它编程模型简单，但要做稳定，关键不在"发请求收响应"，而在于一整套防护：

- 超时是底线，永远不无限等待。
- 重试必须配合幂等，超时不等于失败。
- 连接池隔离 + 熔断，防止局部故障演变成雪崩。
- 降级兜底，保住核心可用性。
- 并行、批量、缓存，降低延迟和往返。

如果把这个模式压缩成一句话：

一问一答看似简单，稳定的关键是超时兜底、幂等重试、隔离熔断、失败降级。

## 15. 场景题

你在做一个电商的「下单」接口，它是一个同步请求-响应接口，用户点击下单后要当场返回成功或失败。

下单流程中需要同步调用三个下游服务：库存服务（扣减库存）、风控服务（校验用户是否异常）、优惠券服务（核销优惠券）。当前实现是串行同步调用这三个服务，平均每个 80ms，下单接口 P99 约 300ms。

最近大促期间，优惠券服务偶发抖动，响应时间飙到 2 秒甚至超时，结果整个下单接口大面积超时，线程池被打满，连不用优惠券的订单也下不了单。

如果让你重新设计这个同步调用链路，你会怎么做？

可以从这几个角度想想：

- 为什么"一个下游抖动"会拖垮"整个下单接口"，根因是什么？
- 在仍然保持同步请求-响应的前提下，你会用哪些手段把 P99 降下来，并防止单个下游故障引发雪崩？
- 三个调用里，哪些必须同步、哪些其实可以异步化？如果改造，要注意什么一致性问题？
- 顺便想想：如果调用优惠券服务超时了，但其实它已经把券核销了，你怎么保证用户不会被重复核销？
