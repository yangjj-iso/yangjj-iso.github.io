如果把大语言模型看成一个函数，那么 Prompt 只是调用时写下的那句请求，而 Context 是模型在这一轮真正能够看到的全部输入。Context Engineering（上下文工程）要解决的问题，就是在有限的上下文窗口里，给模型恰到好处的信息：既足够完成任务，又不会被冗余、冲突和历史噪声淹没。

## 0. 面试 1 分钟回答

如果被问到“Context Engineering 是什么”，可以这样回答：

Context Engineering 是围绕模型输入设计的一套工程方法。它不改变模型结构，而是通过保存、选择、压缩和隔离上下文，让模型在有限的 Context Window 中看到当前任务真正需要的信息，从而提高准确性、稳定性和成本效率。

Prompt Engineering 主要解决“这一轮怎么提问”，Context Engineering 解决“这一轮应该把什么给模型看”。在 Agent 场景中，工具描述、工具结果、历史消息、检索文档和记忆会不断进入上下文，因此上下文管理会直接影响 Agent 后续的决策。一个可靠的系统必须同时设计上下文的来源、优先级、预算、生命周期和安全边界。

一句话总结：

Context Engineering 不是把更多资料塞进 Prompt，而是为模型的下一步行动，组装最相关、最可信、最可控的输入。

## 1. Context 到底是什么

### 1.1 从“模型是一个函数”开始理解

从外部看，大模型很像一个函数：

```text
output = model(input)
```

input 并不只是用户最后输入的那一句话。对一个真实的聊天或 Agent 请求来说，模型看到的内容通常包括：

- 系统指令和安全策略。
- 用户当前问题以及对话中的背景信息。
- 相关文档、数据库记录、检索结果。
- 可用工具的名称、参数说明和调用约束。
- 工具执行后的返回值、错误日志和中间产物。
- 历史消息、阶段性总结和长期记忆。
- 当前任务的状态、已完成步骤和待办事项。

这些内容共同构成了本轮请求的 Context（上下文）。模型只能根据它看到的上下文生成答案或选择下一步动作；没有进入上下文的信息，就相当于没有提供给模型。

### 1.2 Context Window 是容量边界

Context Window（上下文窗口） 是一次模型调用能够容纳的 token 上限。Token 是文本被切分后的基本单位，可能是一个汉字、一个词、一个标点或更小的子词。不同模型、不同接口版本的窗口大小不同，而且通常还要为模型输出预留空间，因此“理论窗口大小”不等于“可以无脑使用的输入容量”。

可以用一个简单的预算公式理解它：

```text
可分配上下文预算
  = 模型窗口上限
  - 系统指令
  - 用户请求
  - 工具定义
  - 输出预留
  - 安全余量
```

比较不同模型的窗口大小时，重点不是某个具体数字，而是：即使窗口越来越大，它仍然是有限资源；为了成本和延迟，我们也不一定会为每个请求选择最大模型。

### 1.3 为什么“把整本产品手册都发过去”仍然不可靠

假设要做一个智能客服，模型需要依据企业产品手册回答问题。最直觉的方案是把所有手册原文放进每一次请求中，但这会同时遇到三个现实问题。

**问题一：窗口总会有上限**

资料规模、历史对话和工具输出会不断增长。长文档、多个附件、代码仓库和长时间 Agent 轨迹很容易超出窗口。即使某些模型支持很长的上下文，系统仍然要考虑输出预算、并发量、延迟和成本。

**问题二：输入太杂乱会降低理解质量**

“能放下”不等于“应该放”。未经筛选的资料可能包含：

- 重复章节和过期版本。
- 对当前问题无关的产品线。
- 互相矛盾的规则。
- 大段表格、日志和工具原始输出。
- 没有来源、时间或权限信息的内容。

模型面对这些信息时，可能抓错重点、混淆版本、平均化多个答案，或者在事实冲突时给出含糊结论。上下文质量首先是信息组织问题，而不只是容量问题。

**问题三：输入越多，成本越高**

大模型调用通常按 token 计费，输入 token 越多，成本和延迟通常越高。在产品化和大规模调用中，一份每次都重复注入的长文档，会被放大成持续的基础设施成本。

因此，工程目标不应是“把所有可能有用的信息都放进去”，而应是：

在正确的时间，把正确的信息，以正确的格式，交给正确的模型。

## 2. Context Engineering：定义、边界与兴起原因

### 2.1 定义

Context Engineering 可以翻译为“上下文工程”。它关注的不是如何重新训练模型，而是如何设计、生成、筛选、压缩、持久化和传递模型输入，让模型在有限窗口内：

- 理解得更准确。
- 输出更稳定、更可控。
- 工具调用更少出错。
- 在同等效果下消耗更少 token。

核心思想可以概括为：

不改变模型结构，只改变模型能看到什么。

这里的“工程”意味着它不只是写一段漂亮的提示词，而是需要处理数据流、状态、权限、预算、故障和评估。上下文是一条动态管道，不是一段静态字符串。

### 2.2 它和 Prompt Engineering 有什么区别

两者不是替代关系，而是关注层次不同：

| 领域 | 主要问题 | 典型对象 |
| --- | --- | --- |
| Prompt Engineering | 这一轮如何把要求说清楚 | 角色、任务、示例、输出格式 |
| Context Engineering | 这一轮把哪些信息给模型看 | 记忆、检索、工具、历史、规则 |
| Agent Engineering | 模型如何感知环境并采取行动 | 工具调用、规划、执行、反馈 |
| Workflow / Loop Engineering | 多步任务如何推进和停止 | 状态、验证器、重试、人工介入 |

例如，“帮我修复这个测试”是 Prompt；把失败日志、相关代码、项目规则和测试命令按优先级放入请求，是 Context；让模型读取代码、修改文件、运行测试并根据结果继续，是 Agent；规定最多尝试五次、测试通过就停止、连续重复失败就升级给人，是 Loop。

### 2.3 为什么这个词最近变得重要

有两个直接原因。

第一，模型能力已经足够强大。很多时候模型回答不理想，并非模型完全不会，而是没有拿到清晰、完整、相关的输入。模型越强，输入质量对最终效果的影响越明显。

第二，Agent 开始大量使用工具。Agent 每执行一次搜索、读文件、运行命令或调用 API，就可能增加一段新的上下文。任务运行时间越长，历史消息、工具结果和中间产物越容易占满窗口，进而影响下一步决策。因此，Agent 的能力不只取决于模型本身，也取决于上下文是否被持续管理。

## 3. 全局地图：四类上下文操作

借鉴 LangChain 的设计思路，把 Context Engineering 归纳为四类操作：

| 操作 | 要解决的问题 | 常见实现 |
| --- | --- | --- |
| 保存 Context | 信息如何跨轮次、跨会话持久化 | 记忆库、状态表、文件、向量库 |
| 选择 Context | 海量信息中哪些应该进入本轮 | 静态规则、RAG、工具路由、重排序 |
| 压缩 Context | 历史和工具结果如何减少占用 | 摘要、截断、滚动摘要、结构化状态 |
| 隔离 Context | 不同模块如何避免相互污染 | 子 Agent、独立会话、权限域、结果协议 |

四者不是互斥开关，而是一条上下文生命周期：

![上下文生命周期：保存、选择、压缩、隔离、执行与记录]({{ "/images/posts/context-engineering/context-lifecycle.svg" | relative_url }})

下面按照这四类操作逐一展开。

## 4. 保存 Context：让信息能够留下来

### 4.1 保存解决的是“持久化”问题

保存 Context 的含义是：先对上下文做筛选或总结，再将它放入内存、硬盘、数据库或其他存储中，等未来真的需要时再取回模型。

例如，用户在一次对话中说：

> 我主要使用 TypeScript，项目采用 pnpm，提交代码前必须运行 pnpm test。

这条信息如果每次都要求用户重新说明，体验很差；如果直接把整段历史对话永远附带给模型，成本又很高。更合理的方式是将它保存为一条结构化记忆：

```json
{
  "memory_id": "pref-001",
  "type": "user_preference",
  "content": "用户偏好 TypeScript；项目使用 pnpm；提交前运行 pnpm test",
  "scope": "user:yangj/project:demo",
  "source": "conversation:2026-06-13T10:00:00+08:00",
  "confidence": 0.92,
  "updated_at": "2026-06-13T10:00:00+08:00"
}
```

下次请求只需要在相关任务中取回这条记忆，而不是注入整段聊天记录。

### 4.2 记忆不是“什么都存”

保存的第一步不是写入，而是判断是否值得写入。通常可以保存：

- 稳定的用户偏好和身份信息。
- 项目级约束、编码规范和已确认的设计决策。
- 长任务中的目标、已完成步骤、失败尝试和待办事项。
- 经过验证的事实以及它的来源和有效期。

通常不应该直接保存：

- 一次性的闲聊。
- 未验证的模型猜测。
- 带有敏感信息但没有权限控制的原文。
- 已过期、与当前项目无关的临时状态。

一个实用的记忆记录至少应带上 scope、source、confidence 和 updated_at。没有来源和时间的记忆，很容易在未来变成无法追责的“幽灵事实”。

### 4.3 保存和选择必须配套

保存只是把信息放到外部，不能自动解决“下一次该取什么”。一个可靠的记忆系统通常还需要：

- 按用户、项目、会话或任务划分作用域。
- 使用关键词、向量、标签或结构化条件进行检索。
- 根据相关性、时效性和可信度重排序。
- 在注入模型前去重、截断和格式化。
- 允许用户查看、修改和删除记忆。

以 ChatGPT 的记忆功能作为例子：记忆库负责保存信息，而未来请求中的相关记忆召回，则属于“选择 Context”。这两个动作应当在系统设计上明确分开。

## 5. 选择 Context：只把相关信息放进本轮

选择 Context 是四类策略中最核心的一类：从海量信息中找出与当前问题最相关的部分，并将它们放入模型上下文。好的选择策略，往往决定了系统的准确性和效率。

选择可以分成静态选择和动态选择。

### 5.1 静态选择：每次都必须在场的规则

静态选择是指把那些永远重要、每次都必须遵守的信息，固定放入每一次请求。它们类似“焊在模型脑子里的系统指令”。

常见内容包括：

- 系统安全规则和拒答边界。
- 当前项目的技术栈和目录约定。
- 代码格式、测试命令和提交规范。
- 输出必须遵循的 schema。
- 工具调用的通用限制。

Cursor 的 rules 文件、Claude Code 的 CLAUDE.md 都属于这类思路。静态上下文应该短小、稳定、优先级明确。把整本开发手册当成“静态规则”会让规则本身成为噪声；静态层只保留那些不管用户问什么都不能违背的内容，其余资料放到动态检索层。

一个静态规则文件可以写成：

```markdown
# 项目规则

- 使用 TypeScript，包管理器为 pnpm。
- 只修改当前任务涉及的目录，禁止删除测试。
- 修改后先运行 pnpm test，再运行 pnpm lint。
- 不得读取或输出 .env、密钥和生产数据。
- 如果需求与现有 API 契约冲突，停止并请求确认。
```

### 5.2 动态选择：像图书管理员一样检索

动态选择是指根据用户问题、当前任务状态和执行阶段，选择最相关的内容。它不是把所有信息塞进模型，而是像一个图书管理员，精准找到当前需要的几页。

动态选择可以用于：

- 从记忆库中召回相关偏好。
- 从文档库中检索产品规则。
- 从代码仓库中定位相关模块。
- 从几十个或几百个工具中挑选本轮最可能使用的工具。
- 根据上一步工具报错，只补充读取相关文件。

### 5.3 RAG 是动态选择的一种典型实现

RAG（Retrieval-Augmented Generation，检索增强生成）常被当作独立技术，但从上下文工程的角度看，它就是“动态选择 Context”的一条重要流水线：

```text
用户问题
  -> 查询改写 / 意图识别
  -> 文档召回
  -> 过滤权限、版本和时间
  -> 重排序
  -> 去重、切片、压缩
  -> 拼装带来源的上下文
  -> 交给模型生成
```

一个最小的伪代码实现如下：

```python
def build_dynamic_context(query, user, budget):
    candidates = retriever.search(query, top_k=30)
    candidates = [item for item in candidates if can_read(user, item)]
    candidates = [item for item in candidates if not item.is_expired]

    ranked = reranker.rank(query, candidates)
    selected = pack_until_budget(ranked, budget=budget,
                                 reserve_source=True,
                                 remove_duplicates=True)

    return render_with_citations(selected)
```

这里的关键不是 top_k=30 这个数字，而是检索结果必须经过权限过滤、版本过滤、去重和预算控制。只按向量相似度召回，可能把旧版本、无权限或与任务目标不一致的文档送给模型。

### 5.4 工具也需要动态选择

当 Agent 拥有几十个工具时，把所有工具名称和完整 schema 都放进每一轮，会产生两类问题：上下文变长，以及模型更容易选错工具。

常用做法是两阶段路由：

```text
用户问题
  -> 小型分类器 / 规则路由
  -> 候选工具集合
  -> 模型选择具体工具并填写参数
```

工具定义还应分层：工具名和一句话用途可以提前提供，只有被选中的工具才注入完整参数 schema。这样既减少 token，也降低工具选择噪声。

## 6. 压缩 Context：让长任务不会越跑越差

### 6.1 为什么 Agent 特别需要压缩

Agent 运行时会积累大量历史消息，最占空间的往往是：

- 模型的长篇输出。
- 工具执行结果。
- 大段源代码和日志。
- 重复的错误堆栈。
- 已经完成、但仍然保留在原始对话中的中间过程。

如果不处理，历史会迅速挤满上下文窗口，后续模型要么超限，要么在大量旧信息中找不到当前重点。

### 6.2 压缩不是简单截断

直接保留最后 N 条消息很便宜，但可能丢掉关键决策。更可靠的压缩应该区分“必须保留”和“可以丢弃”的信息：

| 优先级 | 建议保留的内容 |
| --- | --- |
| P0 | 原始目标、安全约束、权限边界、最终验收标准 |
| P1 | 已确认的事实、关键代码改动、测试结果、外部证据 |
| P2 | 当前假设、未解决问题、下一步计划 |
| P3 | 重复日志、已处理的中间输出、无关闲聊 |

压缩后的摘要最好使用结构化格式，而不是一段没有来源的散文：

```markdown
## Task State

- 目标：修复 UserServiceTest，不修改断言。
- 已确认：数据库字段为 `user_name`，实体映射缺少 `@Column`。
- 已修改：`UserEntity.ts` 增加字段映射。
- 验证结果：目标测试通过，模块测试尚未执行。
- 当前风险：修改可能影响登录查询。
- 下一步：运行完整模块测试并检查登录回归。
- 证据：test-run-2026-06-13-01.log
```

### 6.3 一个可落地的压缩流程

```python
def compact_if_needed(state, model_window):
    usage = count_tokens(state.messages)
    if usage < model_window * 0.80:
        return state

    old_messages = state.messages[:-8]
    recent_messages = state.messages[-8:]

    summary = summarizer.invoke({
        "goal": state.goal,
        "messages": old_messages,
        "required_fields": [
            "facts", "decisions", "changed_files",
            "verification", "open_questions", "next_step"
        ],
        "instruction": "只保留有证据的信息，区分事实和假设"
    })

    return state.replace_messages([
        SystemMessage("历史摘要：\n" + summary),
        *recent_messages,
    ])
```

实现时还要注意：

- 触发阈值不能等到 100% 才压缩，要为输出和工具调用留余量。
- 摘要模型和主模型可以不同，以降低成本。
- 摘要必须保留来源、时间和验证状态。
- 压缩前先把重要状态写入外部存储，避免摘要失败导致信息丢失。
- 对代码、JSON、SQL 等结构化内容，优先保留文件路径、符号名、差异和测试结果，不要只保留自然语言描述。

### 6.4 Auto-compact 的启发

以 Claude Code 的 auto-compact 作为例子：当上下文使用量接近上限时，系统会总结旧上下文、丢弃原始细节，再用摘要降低占用；用户还可以指定压缩时重点保留测试输出和代码改动。

这个例子说明，压缩策略应该由任务决定：

- Coding Agent 优先保留 diff、测试、编译错误和当前文件范围。
- 客服 Agent 优先保留用户约束、订单状态和已确认的政策条款。
- 研究 Agent 优先保留来源、结论、证据和未验证假设。

## 7. 隔离 Context：让不同角色各司其职

### 7.1 隔离解决的是“互相污染”

隔离 Context 的含义是：不同模块、不同角色或不同子任务使用相互独立的上下文，不共享全部历史、工具和记忆。这样可以避免一个子任务的噪声、错误假设或敏感数据污染另一个子任务。

这通常发生在 Multi-Agent 系统中。

### 7.2 Lead Agent 与 Sub-agent

以 Anthropic 的多智能体研究系统为例说明这种架构：

![Lead Agent 拆分研究任务，汇总子 Agent 的证据并形成报告]({{ "/images/posts/context-engineering/lead-subagents.svg" | relative_url }})

每个 sub-agent 有自己的：

- 工具集合。
- 运行历史。
- 记忆和状态。
- 权限范围。
- 输出格式。

Lead Agent 不需要看到每个 sub-agent 的全部原始对话，只需要接收结构化结果、证据、置信度和未解决问题。

推荐使用明确的输入输出协议：

```json
{
  "subtask": "检索产品退款政策",
  "scope": "2025-01-01 之后的正式文档",
  "allowed_sources": ["internal_docs"],
  "output_schema": {
    "answer": "string",
    "evidence": [{"title": "string", "url": "string", "quote": "string"}],
    "uncertainty": ["string"],
    "next_action": "string"
  }
}
```

### 7.3 隔离不等于盲目拆成多个 Agent

多 Agent 会带来额外成本和协调复杂度。只有当任务确实存在职责边界、工具边界或上下文边界时，拆分才有意义。

工程上需要特别注意：

- 有依赖关系的任务优先串联，先得到前一步结果再执行后一步。
- 需要并行探索时，每个 Agent 使用独立工作区或只读数据源。
- 共享信息通过摘要和结构化产物传递，不共享完整聊天记录。
- 最终汇总 Agent 需要检查来源、冲突和不确定性。
- 不同 Agent 的权限应最小化，研究 Agent 不应自动拥有写库或发布权限。

Cognition 的《Don't Build Multi-Agents》并非简单反对 Multi-Agent，而是提醒：如果多个 Agent 并行运行会让上下文和结果难以协调，那么串联执行、缩小上下文、明确职责可能更可靠。

## 8. 把四种策略组合成一条上下文管道

一个可落地的 Context Builder 可以按下面的顺序工作：

1. 规范化用户请求：识别目标、实体、时间和权限。
2. 加载静态规则：系统指令、项目规范、安全边界。
3. 读取任务状态：目标、已完成步骤、失败尝试和下一步。
4. 动态检索：召回相关记忆、文档、代码和工具。
5. 过滤与重排：校验权限、版本、时效、来源和相关性。
6. 计算预算：为工具定义、历史和模型输出预留空间。
7. 压缩或截断：优先去重，再摘要，最后才硬截断。
8. 隔离分发：按 Agent 角色只发送必要内容。
9. 统一渲染：使用清晰的段落、标签、来源和优先级。
10. 调用模型并记录 trace：保存输入版本、输出、工具调用和验证结果。

伪代码可以写成：

```python
def build_context(request, state, policy):
    static_rules = load_static_rules(policy.project)
    task_state = load_task_state(state.task_id)

    memories = retrieve_memories(
        query=request.text,
        scope=[request.user_id, policy.project],
        permissions=request.permissions,
    )
    documents = retrieve_documents(request, permissions=request.permissions)
    tools = route_tools(request, policy.available_tools)

    sections = [
        render("rules", static_rules),
        render("task_state", task_state),
        render("memories", memories),
        render("documents", documents),
        render("tools", tools),
        render("recent_history", state.recent_messages),
    ]

    budget = policy.context_window - policy.output_reserve - policy.safety_margin
    sections = fit_budget(sections, budget)
    return assemble_with_provenance(sections)
```

### 8.1 为什么要统一渲染

同一份信息用不同格式注入，模型的理解稳定性会不同。建议：

- 明确区分“指令”“事实”“工具结果”“候选资料”。
- 为检索内容标注来源、时间和可信度。
- 使用固定顺序，避免每轮拼接顺序随机变化。
- 用 XML、Markdown 标题或 JSON schema 做结构分隔。
- 明确告诉模型哪些内容是参考资料，哪些内容是必须遵守的规则。

例如：

```xml
<system_rules>只能修改当前仓库的 src/ 目录</system_rules>
<task>修复订单查询接口的分页错误</task>
<evidence source="test-log-001">page=2 返回重复记录</evidence>
<retrieved_document source="order-api-v3.md" updated_at="2026-06-01">
  分页参数从 1 开始计数
</retrieved_document>
```

### 8.2 重要信息要带证据链

Context 工程不仅要控制“放多少”，还要控制“凭什么放”。对关键事实，建议保存：

- 来源 URL、文件路径或数据库记录 ID。
- 文档版本和更新时间。
- 检索分数或选择原因。
- 是否经过人工或程序验证。
- 该信息的权限范围和过期时间。

这样模型的最终回答才能引用依据，系统也能在错误发生时追溯是哪一段上下文导致的。

## 9. 一个智能客服的完整例子

假设要实现“查询订单并解释退款政策”的客服 Agent，可以这样设计。

### 9.1 上下文分层

```text
静态层：安全规则、身份认证要求、客服口吻、不可承诺的事项
记忆层：用户语言偏好、已确认的联系方式
动态知识层：当前商品和退款政策的最新版本
任务状态层：订单号、已验证身份、已调用的接口
工具层：订单查询、物流查询、退款申请
历史层：最近几轮对话的压缩摘要
```

### 9.2 一次请求的处理流程

```text
用户：这个订单为什么还不能退款？
  -> 识别意图：退款状态解释
  -> 静态加载：身份和合规规则
  -> 记忆召回：用户语言偏好
  -> 动态检索：订单号相关记录、对应商品政策
  -> 工具路由：只注入订单查询工具和政策查询工具
  -> 调用工具并验证身份
  -> 只把结构化结果返回模型
  -> 模型生成解释和下一步建议
  -> 保存已确认的订单状态，不保存完整敏感响应
```

### 9.3 这比“把所有资料放进 Prompt”好在哪里

- 过期政策不会因为静态全文注入而混入回答。
- 用户无权访问的订单记录会在检索阶段被过滤。
- 工具列表更短，减少错误调用。
- 历史聊天被摘要，成本随对话增长不会线性失控。
- 每个结果都有来源和时间，便于客服解释和审计。

## 10. 评估 Context Engineering 是否有效

不能只看最终回答“感觉不错”。上下文工程需要像其他系统一样做可观测和评估。

### 10.1 效果指标

- 任务成功率：最终是否完成任务。
- 事实正确率：答案是否与权威来源一致。
- 引用覆盖率：关键结论是否能追溯到证据。
- 工具调用成功率：参数是否正确、是否频繁重试。
- 上下文相关性：注入内容中真正被任务使用的比例。
- 冲突率：上下文中是否同时出现相互矛盾的信息。

### 10.2 效率指标

- 每次请求的输入、输出 token。
- 首 token 延迟和端到端延迟。
- 检索、重排序、摘要各阶段的耗时。
- 单个任务的平均模型调用次数。
- 记忆命中率和无效召回率。
- 压缩触发次数及压缩后的 token 降幅。

### 10.3 安全指标

- 越权资料进入 Context 的次数。
- Prompt Injection 被召回或被执行的次数。
- 敏感字段脱敏覆盖率。
- 高风险工具被拦截、审批和审计的比例。
- 跨用户、跨项目的记忆污染次数。

建议为每次模型调用记录一份可脱敏的 trace：

```json
{
  "trace_id": "ctx-20260613-001",
  "task_id": "refund-123",
  "static_tokens": 820,
  "retrieved_items": ["policy-v3", "order-123"],
  "history_tokens_before": 8200,
  "history_tokens_after": 2100,
  "tools_exposed": ["get_order", "get_refund_policy"],
  "model_result": "grounded",
  "sources": ["policy-v3", "order-service"]
}
```

## 11. 常见误区与工程对策

### 11.1 误区：上下文越长，效果越好

更长的上下文不代表更高的信息密度。对策是建立预算、优先级和去重规则，并通过 A/B 测试比较“全部注入”和“精选注入”的真实效果。

### 11.2 误区：只依赖向量检索

向量相似度无法独立处理权限、版本、时效和逻辑冲突。对策是把语义召回放在第一步，后面补充元数据过滤、重排序、来源校验和冲突检测。

### 11.3 误区：把所有规则写进一个超长规则文件

静态规则太长会吞噬每次请求的预算，也会让真正重要的约束被淹没。对策是只固定注入不可违背的核心原则，其他内容按任务动态加载。

### 11.4 误区：压缩就是丢掉旧消息

盲目截断可能丢掉决策依据、测试结果和安全边界。对策是先结构化抽取，再保留最近对话，最后才对低优先级内容做截断。

### 11.5 误区：共享一个全局记忆库

不同用户、项目和 Agent 共用未经隔离的记忆，会造成隐私泄露和事实污染。对策是为记忆增加作用域、权限和有效期，并在召回时强制过滤。

### 11.6 误区：检索内容天然可信

文档、网页和代码注释也可能包含 Prompt Injection。对策是把检索结果当作“不可信数据”，不能让资料中的指令覆盖系统规则；高风险动作必须经过工具层权限校验和人工确认。

### 11.7 误区：多 Agent 越多越强

Agent 数量增加后，通信、汇总和上下文协调成本也会增加。对策是先用单 Agent + 清晰上下文解决问题，只有当职责、工具或权限确实需要分离时才拆分，并让子 Agent 输出紧凑的结构化结果。

## 12. Context Engineering、RAG、Memory 和 Agent 的关系

这几个概念经常被混在一起，可以用下面的方式区分：

- Memory：信息长期存在哪里
- RAG：如何从外部知识中召回相关信息
- Context Engineering：如何决定本轮给模型什么、以什么顺序和格式给
- Agent：模型如何使用这些上下文去调用工具并影响环境

RAG 和 Memory 都可以是上下文工程的组件，但上下文工程还包括静态规则、工具路由、历史压缩、上下文隔离、权限过滤和预算控制。它是一个系统层的总称，而不是某一个具体算法。

## 13. 推荐的落地路线

### 阶段一：先把上下文画出来

针对一个真实任务列出：

- 模型本轮能看到哪些输入。
- 哪些输入是固定的，哪些是动态的。
- 哪些内容最占 token。
- 哪些信息在不同角色之间不应共享。
- 哪些结论需要保留来源。

很多问题在这一步就能被发现：例如把完整工具结果重复塞入、把过期规则和新规则混在一起、把用户私密信息写入全局记忆等。

### 阶段二：建立最小 Context Builder

先实现四个能力：

- 静态规则加载。
- 动态检索和权限过滤。
- 历史摘要和 token 预算。
- 每次调用的输入输出 trace。

不要一开始就同时引入复杂的多 Agent、向量数据库和自动记忆。先证明“精选上下文”比“全部历史”更稳定。

### 阶段三：增加验证和回放

为典型任务建立离线数据集，固定用户请求、可用资料和期望结果，然后比较不同上下文策略：

- 全量历史 vs. 摘要历史。
- 全量工具 vs. 动态工具路由。
- 纯向量检索 vs. 向量 + 元数据过滤。
- 单 Agent vs. 隔离的子任务 Agent。

所有策略都要在准确率、成本、延迟和安全性之间做综合评估。

### 阶段四：再考虑多 Agent 和自动化

当单 Agent 已经能稳定运行，且确实存在职责和权限边界，再引入 Lead Agent、Sub-agent、串联工作流和人工审批。Context Engineering 的目标是降低复杂度，而不是把复杂度藏进更多 Agent。

## 14. 设计检查清单

设计一个上下文管道前，至少检查：

- 是否定义了当前任务真正需要的信息。
- 是否区分静态规则、动态资料、历史和记忆。
- 是否为输入、工具和输出预留 token 预算。
- 是否过滤权限、版本、时效和重复内容。
- 是否给关键事实保存来源和验证状态。
- 是否有压缩触发阈值和保留优先级。
- 是否把工具按任务动态路由，而不是全部暴露。
- 是否隔离不同用户、项目和 Agent 的上下文。
- 是否能防止检索资料中的指令覆盖系统规则。
- 是否记录每次选择、压缩和注入的 trace。
- 是否同时评估准确率、成本、延迟和安全指标。
- 是否有失败时的降级方案和人工介入点。

## 15. 总结

Context 代表模型的输入，Context Window 代表模型输入容量的边界。真正的问题不只是“能不能装下”，还包括“内容是否相关、是否清晰、是否可信、是否值得付费”。

Context Engineering 可以归纳成四个动作：

| 动作 | 记忆口诀 | 关键问题 |
| --- | --- | --- |
| 保存 | 需要时找得到 | 信息如何跨轮次持久化 |
| 选择 | 本轮只拿相关的 | 哪些资料、工具和记忆值得注入 |
| 压缩 | 长任务不能越跑越胖 | 历史如何保留重点并降低占用 |
| 隔离 | 不同角色不要互相污染 | 谁可以看到哪些上下文和工具 |

如果只记住三句话：

- Context 不是 Prompt 的同义词，而是模型在这一轮看到的全部信息。
- 上下文越多不一定越好，相关、可信、结构化比冗长更重要。
- Agent 的执行质量，往往取决于系统能否持续为下一步构造恰到好处的上下文。

上下文工程的本质，是把“模型能看到什么”从临时拼接的字符串，升级为有预算、有来源、有权限、有生命周期、可观测和可验证的系统能力。
