## 一句话先说清楚

Harness Engineering（驾驭工程），就是给 AI 智能体套上“缰绳”的系统工程。

Harness 原本指马具，比如缰绳、马鞍、嚼子。这个比喻很贴切：大模型像一匹速度很快、力量很强的马，能力惊人，但方向不总是稳定。Harness Engineering 要做的，不是让这匹马再长两条腿，而是给它修好路、装护栏、设路标、配补给，让它能持续、可靠地跑在正确方向上。

它背后的核心哲学可以概括成八个字：

> 人类掌舵，智能体执行。

这也是 Harness Engineering 与“换一个更强模型”最根本的区别。它优化的不是模型权重，而是模型运行时所处的环境、约束、反馈和恢复机制。

## 为什么它会在 2026 年突然爆火？

原因很简单：越来越多团队发现，真正卡住 AI 生产力的瓶颈，不再只是模型本身，而是围绕模型的工程系统没有跟上。

下面是几个被频繁引用的结果：

| 团队/项目 | 操作方式 | 核心成果 |
| --- | --- | --- |
| OpenAI（Codex） | 3 人团队，5 个月主要依靠 Agent 开发 | 生成 100 万行代码，合并 1500 个 PR，人均每日 3.5 个 PR |
| LangChain | 底层模型参数不变，只优化 Harness | Terminal Bench 2.0 得分从 52.8% 提升到 66.5%，排名从第 30 名升到第 5 名 |
| Can.ac 实验 | 只修改 Harness 的工具调用格式 | Grok Code Fast 1 得分从 6.7% 提升到 68.3%，并且 16 个模型普遍提升 |

这些案例共同说明一件事：

问题并不只在“模型会不会写代码”，更在“这个智能体有没有被放进一个足够好的工程系统里”。

## AI 工程范式的三次跃迁

如果把过去几年的 AI 工程演进放在一起看，Harness Engineering 并不是凭空出现的，而是前两个阶段自然推出来的结果。

| 范式阶段 | 活跃期 | 核心问题 | 优化对象 | 形象类比 |
| --- | --- | --- | --- | --- |
| Prompt Engineering | 2023–2024 | 怎么把指令说清楚 | 提示词措辞、结构、模板 | 对马喊话的技巧 |
| Context Engineering | 2025 | 怎么给 AI 喂对信息 | 文档、代码片段、知识库、检索 | 给马看的导航地图 |
| Harness Engineering | 2026 起 | 怎么让 Agent 稳定交付 | 约束、反馈循环、控制系统 | 给马造高速公路和护栏 |

前两个阶段解决的，更多是“说清楚”和“喂对信息”的问题；Harness Engineering 解决的，则是一个更接近真实生产环境的问题：

当 AI 从一次性回答问题，变成持续执行任务的智能体时，怎样让它稳定、安全、可恢复地完成工作。

## 为什么 AI 智能体总是容易“翻车”？

很多团队在真实项目里都踩到了类似的坑，典型问题大致有三类：

### 1. 试图一步到位

Agent 很容易在一个会话里同时塞进太多目标，结果就是上下文被挤爆，过程失控，最后只留下半成品。

### 2. 过早宣布胜利

智能体看到某些功能“看起来能用了”，就倾向于直接判定任务完成，忽略剩余的核心逻辑、边界处理和联动部分。

### 3. 测完单点就当全部完成

写完代码、跑过几个单元测试，不代表系统已经可用。缺少端到端验证时，很多问题只会在集成阶段暴露出来。

除此之外，还有一个更隐蔽但更危险的问题：

### 4. AI 是模式复制放大器

如果代码库里本来就有坏味道、架构漂移或隐性技术债，Agent 往往不会主动纠正它们，反而会高效地复制并放大这些问题。没有约束的 Harness，不是提效工具，而可能是技术债加速器。

## Harness Engineering 的四大核心组件

一套成熟的 Harness，通常离不开下面四道“护栏”。

### 1. 上下文工程：给智能体一本真正有用的新员工手册

不是把一大堆规范一次性塞给它，而是给它一个稳定、简洁、可按需扩展的入口。

- 不要把 AGENTS.md 写成 1000 页百科全书
- 要把 AGENTS.md 设计成索引页，让 Agent 知道该去哪里找信息
- 详细规范拆到子文档里，按任务场景动态加载

上下文不是越多越好，而是越相关越好。过大的静态文档只会挤占任务空间，最终变成“陈旧规则坟场”。

### 2. 架构约束：把规则变成机器能执行的缰绳

架构规则如果只写在文档里，最终一定会被绕过；要让智能体真正遵守规则，最有效的方式是把规则编码到工具链里。

例如：

- 明确依赖分层：Types -> Config -> Repo -> Service -> Runtime -> UI
- 用 Linter、类型系统和 CI 做强约束
- 规则报错信息里不仅告诉它“错了”，还要告诉它“为什么错”和“应该怎么改”

这样，Agent 才有机会基于反馈自行修正，而不是反复撞墙。

### 3. 反馈循环：让智能体在交付前就看到自己的问题

传统做法是人来做 Code Review；在 Harness 体系下，更重要的是建立自动反馈回路。

一个典型闭环可能是：

- 本地自检
- 运行测试
- 请求额外审查
- 根据反馈修复
- 循环直到通过

如果测试本身失效，比如 AI 写出的测试把明显 Bug 放过去了，那么 Harness 需要判定“测试无效”，而不是盲信“测试通过”。

### 4. 熵管理：持续回收混乱，而不是等系统烂掉

随着代码演进，文档会过时、架构会腐化、约定会漂移，这些都是系统熵的一部分。

因此，成熟 Harness 不只关注“当前任务有没有完成”，还会持续处理下面这些问题：

- 代码与文档是否一致
- 是否出现重复实现和结构漂移
- 是否存在积累中的技术债
- 是否需要自动提交修复 PR 或触发重构建议

技术债不是抽象风险，它更像高息贷款。越晚处理，成本越高。

## 成熟 Harness 的六层架构

如果继续往下拆，一套完整的 Harness 系统，通常可以分成六层：

### 第 1 层：上下文管理

核心问题是信息如何选择、裁剪和注入。重点不是“给多少”，而是“给什么最有用”。

### 第 2 层：工具系统

这一层关注三个问题：

- 给 Agent 什么工具
- 什么时候允许它调用工具
- 工具返回结果如何重新整理后再喂回上下文

工具不是越多越好。工具过少，能力不足；工具过多，反而会被滥用。

### 第 3 层：执行编排

这一层解决“下一步该干什么”。常见闭环是：

```text
规划 -> 执行 -> 分析缺口 -> 再规划
```

如果没有编排，智能体就容易在长任务中迷失方向。

### 第 4 层：状态与记忆

这一层保存的是智能体持续工作的“上下文骨架”，包括：

- 当前任务进行到哪一步
- 会话期间已经调研出的中间结果
- 长期偏好与稳定约定，比如语言、框架、编码规范

### 第 5 层：评估与观测

系统不能只会做事，还要知道自己是否做对了。常见能力包括：

- 环境验证
- 自动测试
- 日志和指标
- 输出验收
- 错误归因

### 第 6 层：约束与恢复

最后一层关心的是失败控制能力：

- 哪些事情能做，哪些不能做
- 输出前如何检查
- 失败后如何重试、回滚或切换到稳定路径

真正可用的智能体系统，不是“永不犯错”，而是“犯错后不会失控”。

## 大厂在怎么做？

### Anthropic 的两个关键发现

第一是上下文焦虑。长时间运行后，上下文不断膨胀，信息质量下降，智能体会越来越混乱。

第二是自评失真。如果生产和验收都由同一个 Agent 完成，它对“结果是否真的正确”的判断往往不可靠。

### OpenAI 的工程哲学

一个非常重要的变化是：工程师的重心，正在从“亲手写每一行代码”，转向“设计能让 Agent 稳定工作的环境”。

在这种模式下，工程师更像环境建筑师，主要做三件事：

- 拆分任务，把大需求拆成 Agent 能理解和执行的小任务
- 补齐能力，Agent 一旦失败，不是让它更努力，而是分析环境里少了什么能力
- 建立反馈，让 Agent 能真正看到自己产出的效果

### AGENTS.md 的渐进式披露

很多团队一开始会把规范、架构、约定、流程全部塞进一个超大 AGENTS.md。问题在于，上下文窗口本身是稀缺资源，塞太满就等于什么都没强调。

更成熟的做法是：

- AGENTS.md 只保留核心索引和最稳定的规则
- 更细的内容拆到子文档
- 按任务需要动态引入

这就是“渐进式披露”的工程化版本。

## 2026 年形成的六个行业共识

| 序号 | 共识结论 | 核心依据 |
| --- | --- | --- |
| 1 | 瓶颈在基础设施，不在模型智能 | 仅改工具格式，就可能带来数量级提升 |
| 2 | 文档必须是活的反馈循环 | 静态文档很快过时，动态维护才有价值 |
| 3 | 思考与执行必须分离 | 单一上下文窗口很难稳定承载复杂项目 |
| 4 | 上下文不是越多越好 | 大而全指令文件会挤占任务空间 |
| 5 | 约束必须自动化 | 人工 Review 是瓶颈，护栏必须嵌入 Linter、CI、类型系统 |
| 6 | 工程师角色正在转变 | 从代码编写者转向环境建筑师 |

## Harness 和传统 Agent 框架是什么关系？

很多人会把 Harness 和 LangGraph、AutoGen、CrewAI 这类框架混为一谈，但它们解决的并不是同一层问题。

```text
┌─────────────────────────────────────────┐
│   Harness Layer（驾驭层）                │
│   约束 · 反馈循环 · 上下文工程 · 熵管理  │
├─────────────────────────────────────────┤
│   Agent Frameworks                      │
│   (LangGraph / AutoGen / CrewAI)        │
├─────────────────────────────────────────┤
│   SDK / API                             │
│   (OpenAI / Anthropic / Gemini / 国产)  │
├─────────────────────────────────────────┤
│   Foundation Model                      │
│   (GPT-5 / Claude 4 / DeepSeek / 通义)  │
└─────────────────────────────────────────┘
```

可以这样理解：

- 传统 Agent 框架解决的是：怎么把智能体搭起来
- Harness 层解决的是：搭起来以后，怎么让它可靠、安全、可持续地运行

所以 Harness 不是替代框架，而是站在框架之上的控制层。

## 如果从零落地，应该怎么做？

视频里给了一条很实用的分阶段路线图，可以直接拿来当团队实施参考。

### P0：先把最基本的护栏搭起来

- 创建 AGENTS.md，控制在 50 到 100 行，做成目录而不是百科全书
- 实施自定义 Linter，把架构约束编码进检查流程
- 建立自动化测试管道，至少覆盖单元测试、集成测试和结构测试

### P1：让系统具备跨会话连续性和真实验收能力

- 用 progress.json 或 feature_list.md 保存任务进度和跨会话记忆
- 部署端到端验证能力，比如浏览器自动化、日志查询和行为确认
- 将 Orchestrator 与 Worker 分离，降低上下文污染

### P2：开始治理长期熵增问题

- 部署熵管理 Agent，跟踪技术债、文档漂移和自动重构机会
- 建立“是否真的做对”的行为验证体系
- 沉淀棕地项目接入 Harness 的迁移方法论

## 还有哪些问题没有标准答案？

Harness Engineering 很火，但它并不是一套已经彻底成熟的标准答案。目前至少还有三个明显空白区：

### 1. 棕地项目怎么改造？

很多成功案例都来自绿地项目，但现实中的大多数团队面对的是多年历史遗留系统。如何在不推翻重来的前提下引入 Harness，仍然是难题。

### 2. 如何系统化验证“做对了”？

现在大家更擅长“防止做错”，比如限制越权、避免乱改、补齐测试；但如何高置信地验证“这件事情真的完成了，而且行为符合预期”，还缺少成熟范式。

### 3. 如何保证长期可维护性？

即使某次交付功能是对的，也不意味着系统在长期上是健康的。怎样避免“功能正确但架构持续腐烂”的代码进入主分支，是更难的工程问题。

## 总结：它不是模型技巧，而是系统设计能力

Harness Engineering 的真正意义，不在于发明了一个新术语，而在于它把 AI 开发的关注点，从“怎么让模型更聪明”，推进到了“怎么让模型在真实工程里稳定工作”。

这背后有几个值得记住的判断：

| 问题 | 更适合关注的方向 |
| --- | --- |
| 指令说不清 | Prompt Engineering |
| 信息喂不准 | Context Engineering |
| 智能体交付不稳定 | Harness Engineering |

可以把它理解成这样：

- Prompt Engineering 解决“怎么说”
- Context Engineering 解决“给什么信息”
- Harness Engineering 解决“如何持续把事做成”

最后留下三点结论：

- 模型越强，Harness 往往越重要，因为更强能力也意味着更大破坏半径。
- 真正的 AI 工程能力，正在从写代码本身，转向设计环境、约束和反馈系统。
- 未来团队之间拉开差距的关键，不只是“谁用上了 AI”，而是“谁更会驾驭 AI”。
