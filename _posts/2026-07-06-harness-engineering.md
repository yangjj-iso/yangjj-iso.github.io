LangChain 没有换底层模型，只改了模型外面那一层工程系统，Terminal Bench 2.0 的得分就从 52.8% 涨到了 66.5%。类似的结果在 2026 年接连出现，这一层也有了自己的名字：Harness Engineering（驾驭工程）。

Harness 原意是马具。模型能力很强，但放进真实工程里跑长任务，方向和稳定性都靠不住。Harness Engineering 不碰模型权重，关心的是模型运行时所处的环境：它能看到什么、能调用什么、做完怎么验证、出错怎么恢复。常被引用的一句概括是“人类掌舵，智能体执行”。

## 几组被频繁引用的数据

| 团队/项目 | 操作方式 | 核心成果 |
| --- | --- | --- |
| OpenAI（Codex） | 3 人团队，5 个月主要依靠 Agent 开发 | 生成 100 万行代码，合并 1500 个 PR，人均每日 3.5 个 PR |
| LangChain | 底层模型参数不变，只优化 Harness | Terminal Bench 2.0 得分从 52.8% 提升到 66.5%，排名从第 30 名升到第 5 名 |
| Can.ac 实验 | 只修改 Harness 的工具调用格式 | Grok Code Fast 1 得分从 6.7% 提升到 68.3%，并且 16 个模型普遍提升 |

后两个案例里模型都没变，变的是围绕模型的工程系统。Can.ac 的实验只动了工具调用格式，得分就差了十倍。越来越多团队发现，卡住 AI 生产力的已经不只是模型本身。

这条线索往前看也很清楚。2023–2024 年大家琢磨 Prompt Engineering，关心怎么把指令说清楚，优化的是提示词的措辞、结构和模板；2025 年重心转到 Context Engineering，关心给模型喂哪些文档、代码片段、知识库和检索结果。到 2026 年，AI 从一次性回答问题变成持续执行任务的 Agent，问题就变成了怎样让它稳定、安全、可恢复地把活干完，要优化的是约束、反馈循环和控制系统。

## Agent 常见的翻车方式

真实项目里的坑大致有三类。一是想一步到位，一个会话塞进太多目标，上下文被挤爆，过程失控，最后留下半成品。二是过早宣布胜利，看到功能“看起来能用了”就判定完成，剩下的核心逻辑、边界处理和联动部分被晾在一边。三是测完单点就当全部完成，写完代码、跑过几个单元测试不代表系统可用，缺少端到端验证，问题要到集成阶段才暴露。

还有一个更隐蔽的：Agent 会放大代码库里已有的模式。仓库里本来就有坏味道、架构漂移或隐性技术债，它往往不会主动纠正，反而会高效地复制。没有约束的话，Agent 很容易变成技术债加速器。

## 四个核心组件

### 上下文：AGENTS.md 是索引，不是百科全书

上下文要相关，不是越多越好。很多团队一开始会把规范、架构、约定、流程全塞进一个超大的 AGENTS.md，可上下文窗口本身是稀缺资源，塞太满就等于什么都没强调，过时之后还会变成“陈旧规则坟场”。

更成熟的做法是渐进式披露：AGENTS.md 只保留核心索引和最稳定的规则，告诉 Agent 该去哪里找信息；详细规范拆到子文档里，按任务场景动态加载。

### 架构约束：写进工具链

只写在文档里的架构规则，迟早会被绕过。要让 Agent 真正遵守，就把规则编码进工具链：明确依赖分层（Types -> Config -> Repo -> Service -> Runtime -> UI），用 Linter、类型系统和 CI 做强约束。

报错信息也要认真写，除了告诉它“错了”，还要说明为什么错、应该怎么改。这样 Agent 才能根据反馈自己修正，不至于反复撞墙。

### 反馈循环

传统做法靠人做 Code Review。在 Harness 体系里，更重要的是建立自动反馈回路：本地自检、运行测试、请求额外审查、根据反馈修复，循环直到通过。

还要防着测试本身失效。如果 AI 写的测试把明显的 Bug 放了过去，Harness 应该能判定“测试无效”，不能盲信“测试通过”。

### 熵管理

代码不断演进，文档会过时，架构会腐化，约定会漂移。成熟的 Harness 除了看当前任务有没有完成，还会持续检查代码与文档是否一致、有没有重复实现和结构漂移、技术债是否在累积，必要时自动提交修复 PR 或给出重构建议。技术债像高息贷款，越晚处理成本越高。

## 六层架构

再往下拆，一套完整的 Harness 大致可以分成六层：

- **上下文管理**：信息如何选择、裁剪和注入，重点是给什么最有用。
- **工具系统**：给 Agent 什么工具、什么时候允许调用、返回结果怎样整理后再喂回上下文。工具太少能力不足，太多又容易被滥用。
- **执行编排**：决定下一步该干什么。没有编排，Agent 在长任务里很容易迷失方向。
- **状态与记忆**：当前任务进行到哪一步、会话中调研出的中间结果，以及语言、框架、编码规范这类长期偏好和稳定约定。
- **评估与观测**：环境验证、自动测试、日志和指标、输出验收、错误归因，让系统知道自己有没有做对。
- **约束与恢复**：哪些事能做、哪些不能做，输出前如何检查，失败后如何重试、回滚或切换到稳定路径。

其中执行编排最常见的闭环是：

```text
规划 -> 执行 -> 分析缺口 -> 再规划
```

Agent 系统总会犯错，可用的标准是犯错之后不会失控。

## 大厂的做法

Anthropic 提到过两个问题。一个是上下文焦虑：长时间运行后上下文不断膨胀，信息质量下降，Agent 越来越混乱。另一个是自评失真：生产和验收由同一个 Agent 完成时，它对结果是否真的正确的判断往往不可靠。

OpenAI 强调的是工程师角色的变化，重心从亲手写每一行代码，转向设计能让 Agent 稳定工作的环境，有点像环境建筑师。具体是三件事：把大需求拆成 Agent 能理解和执行的小任务；Agent 失败时，先分析环境里缺了什么能力并补上，而不是让它“更努力”；建立反馈，让 Agent 真正看到自己产出的效果。

## 和 Agent 框架的关系

Harness 常被和 LangGraph、AutoGen、CrewAI 这类框架混为一谈，其实它们处在不同的层：

```text
┌─────────────────────────────────────────┐
│   Harness Layer（驾驭层）                │
│   约束 · 反馈循环 · 上下文工程 · 熵管理  │
├─────────────────────────────────────────┤
│   Agent Frameworks                      │
│   (LangGraph / AutoGen / CrewAI)        │
├─────────────────────────────────────────┤
│   SDK / API                             │
│   (OpenAI / Anthropic / Gemini / 国产)  │
├─────────────────────────────────────────┤
│   Foundation Model                      │
│   (GPT-5 / Claude 4 / DeepSeek / 通义)  │
└─────────────────────────────────────────┘
```

Agent 框架解决怎么把智能体搭起来，Harness 关心搭起来以后怎样让它可靠、安全、可持续地运行。它是框架之上的控制层，并不替代框架。

## 从零落地的路线图

视频里给了一条分阶段路线图，我觉得可以直接拿来当团队实施的参考。

### P0：基本护栏

- 创建 AGENTS.md，控制在 50 到 100 行，做成目录而不是百科全书
- 实施自定义 Linter，把架构约束编码进检查流程
- 建立自动化测试管道，至少覆盖单元测试、集成测试和结构测试

### P1：跨会话连续性和真实验收

- 用 progress.json 或 feature_list.md 保存任务进度和跨会话记忆
- 部署端到端验证能力，比如浏览器自动化、日志查询和行为确认
- 将 Orchestrator 与 Worker 分离，降低上下文污染

### P2：治理长期熵增

- 部署熵管理 Agent，跟踪技术债、文档漂移和自动重构机会
- 建立“是否真的做对”的行为验证体系
- 沉淀棕地项目接入 Harness 的迁移方法论

## 还没有标准答案的问题

Harness Engineering 远没有成熟到有标准答案，至少还有三块空白。

第一是棕地项目怎么改造。成功案例大多来自绿地项目，而现实中多数团队面对的是多年的遗留系统，怎样不推翻重来就引入 Harness，仍然是难题。

第二是怎样系统化地验证“做对了”。现在大家更擅长防止做错，比如限制越权、避免乱改、补齐测试；但要高置信地确认一件事真的完成、行为符合预期，还缺少成熟的方法。

第三是长期可维护性。某次交付功能正确，不代表系统长期健康。怎样挡住“功能正确但架构持续腐烂”的代码进入主分支，是更难的工程问题。

模型越强，Harness 往往越重要，因为能力更强，出错时的破坏半径也更大。对工程师来说，要花心思的地方也在跟着变，从写代码本身，慢慢转到设计环境、约束和反馈系统上。
